MHL on EKS — Delivery Plan

Six phases to carry the mhl MCP server from “one process on one host” to an autoscaled EKS Deployment serving many teams — with every infrastructure backend (DynamoDB, Redis, SQS) living outside the language, as a pinned external extension.

constraint: no infra deps in the runtime core invariant: single-replica deploy works at every phase, zero config

The organising principle: one seam

The runtime core already has the right instinct — internal/extension is a dependency-free, JSON-only contract (Extension → Instance.Call) that MCP and A2A are themselves being migrated onto. The plan extends that same seam to state.

Core keeps the interfaces and a built-in disk / in-memory implementation of each — so mhl run and a one-pod mhl serve need no database and no configuration. A cluster deployment points those same interfaces at an external extension of kind store, and the DynamoDB or Redis code ships as a separate, sha256-pinned binary that the runtime never links.

Why the store backend is an extension but JWT verification is not. A store backend is a swappable I/O detail with no trust implications — perfect for an out-of-process, pinned binary. Token verification decides who a caller is; delegating that to an unpinned child process widens the trust boundary. It stays in core, behind a TokenVerifier interface with a JWKS default.

The phases

Each phase ships on its own and preserves the invariant: a single replica behind API Gateway keeps working with no database and no new flags. The gap numbers refer to the architecture note.

Goal

Phase 3 The store extension contract

Let the four interfaces be backed by an external extension; ship two reference backends.

Phase 4 Distributed run execution

Goal
N replicas behind a round-robin load balancer, correctly.
Changes
Cross-pod cancel: run/cancel writes cancelRequested to the store; the owning pod already checks ctx.Err() at each step boundary — also poll that flag there. Live progress across pods: the owner writes step / stepIndex to the store on each OnStep, so a non-owner run/status returns near-real-time state, not just committed checkpoints. Lease-based ownership: an owner renews a lease; on expiry (pod died mid-run) another pod resumes from the last checkpoint. Decide per load test whether the queued pool is cluster-wide (any pod drains it) or per-pod with the HPA sizing the fleet.

unchanged — the lease and flags are no-ops with one owner and the in-memory registry.

Language core vs. external extension

The dividing test: does it decide trust, or does it just move bytes? Trust decisions and process lifecycle stay in core; swappable I/O and vendor-specific glue become extensions.

Stays in the runtime coreShips as an external extension
The StateStore / SessionStore / RunRegistry / Lease interfaces, plus the built-in disk + in-memory implementation DynamoDB, Redis, S3, Postgres backends for those interfaces (kind store)
Health / readiness, drain, graceful shutdown, checkpoint-on-exit — process lifecycle Any cloud-specific credential or endpoint-discovery dance beyond secret.resolve + permissions.network
Concurrency limiting, the queued state, run scheduling policy A cluster-wide queue backend (SQS) if Phase 4 needs one — same store family or a sibling queue kind
TokenVerifier and its JWKS / JWT / trusted-header modes — a trust boundary — never; token verification is not delegated to a pinned binary
OpenTelemetry instrumentation (the spans and metrics themselves); OTLP export configured by standard env Optional: a bespoke metrics / trace exporter only if you refuse an OTel SDK dependency in core (not recommended)
The approvers: language surface and its evaluation against the principal The identity provider itself (Cognito, the team IdP) — already external, upstream of API Gateway

The store extension, concretely

Kind store, one declaration per backend, discovered in the serve directory the same way workflows are. Sketch of the manifest and the call the adapter makes on every checkpoint:

// extension.json  (mhl-store-dynamodb)
{
  "id": "com.acme.mhl-store-dynamodb",
  "version": "0.1.0",
  "api_version": "1",
  "executable": "bin/store-dynamodb",
  "declarations_file": "declarations.json",
  "permissions": {
    "network": ["dynamodb.us-east-1.amazonaws.com"],
    "secrets": ["env(\"AWS_ROLE_ARN\")", "env(\"AWS_WEB_IDENTITY_TOKEN_FILE\")"]
  }
}

// .mh in the serve dir
extension store Backend {
  table:  "mhl-serve-state"
  region: "us-east-1"
}

// adapter -> Instance.Call on each OnStep / checkpoint write
call { declaration: Backend, operation: "cas",
       named_args: { key: "run//checkpoint", expect: , value:  } }

Open protocol questions to settle in Phase 3, all small and additive:

  • Server-lifetime processes. The child must outlive a run and restart with backoff instead of failing after three crashes. A manifest flag ("lifetime": "server") or a serve-side policy.
  • Hot-path cost. A pipe round-trip per checkpoint step is the concern. Benchmark first; mitigate with a write-through cache in the adapter (extension is the source of truth, reads are served locally) and batched flushes.
  • Watch. Cross-pod cancel and live status want push. Ship poll-only in v1; add a subscribe / event shape if polling latency hurts.
  • IRSA vs. “no ambient environment.” The AWS SDK in the extension wants AWS_WEB_IDENTITY_TOKEN_FILE / AWS_ROLE_ARN. Pass them through the manifest env allowlist, or add a host capability that mints them. Decide before writing the DynamoDB backend.
  • Distribution in EKS. Extensions are sha256-pinned and vendored under .mhl/extensions/. In a container that means baking them into the image or an init container — document it; there is no runtime download.
