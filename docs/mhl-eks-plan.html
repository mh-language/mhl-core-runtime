MHL on EKS — Delivery Plan

Six phases to carry the mhl MCP server from “one process on one host” to an autoscaled EKS Deployment serving many teams — with every infrastructure backend (DynamoDB, Redis, SQS) living outside the language, as a pinned external extension.

constraint: no infra deps in the runtime core invariant: single-replica deploy works at every phase, zero config

The organising principle: one seam

The runtime core already has the right instinct — internal/extension is a dependency-free, JSON-only contract (Extension → Instance.Call) that MCP and A2A are themselves being migrated onto. The plan extends that same seam to state.

Core keeps the interfaces and a built-in disk / in-memory implementation of each — so mhl run and a one-pod mhl serve need no database and no configuration. A cluster deployment points those same interfaces at an external extension of kind store, and the DynamoDB or Redis code ships as a separate, sha256-pinned binary that the runtime never links.

Three different questions, three different homes. A store backend is swappable I/O with no trust implications — an out-of-process pinned extension. Who a caller is (token / JWT verification) is a trust boundary the runtime must not delegate to an unpinned binary — it stays in core behind a TokenVerifier, which only extracts a principal. Whether that caller may do this (may they resume run R?) is dynamic policy with live IdP-group and on-call state — it lives in Istio / OPA / the gateway authorizer, never as a list in a .mh file.

The phases

Each phase ships on its own and preserves the invariant: a single replica behind API Gateway keeps working with no database and no new flags. The gap numbers refer to the architecture note.

Status: Phases 0–2, Phase 3a and Phase 4 are complete on branch feature/mcp-http-transport (full test + functional gate green, including -race; e2e smoke with the store-fs reference extension and mhl run / mhl lint). Durable run/session state can live in a shared external store, and a step's timeout clause makes a runaway or orphaned run self-terminate on any pod. Phase 3b/3c (restart policy, hot-path cache, real backends) and the optional Phase 5 (cluster ergonomics, client longevity) remain.

Phase 1 Kubernetes-native (single pod) ✓ done

Goal
Make one replica a well-behaved citizen: probes, drain, backpressure, telemetry.
Landed
Probes — GET /healthz (liveness, stays 200 while draining) + GET /readyz (503 once shutdown begins), unauthenticated, in internal/mcpserver/health.go. Drain — --drain-timeout / MHL_SERVE_DRAIN_TIMEOUT (0 = today's immediate cancel); async runs descend from a runsCtx the drain path controls, so a synchronous tools/call still dies at once on SIGTERM; a draining server refuses new run/start / tools/call with -32000. Shutdown checkpoint — a cancelled run whose workflow set checkpoint { enabled: true } without per_step still leaves a resume point. Observability — log/slog JSON lifecycle lines keyed by runId + owner; run/logs { runId, since } from a per-run 64 KiB ring buffer (also teed to stderr); GET /metrics Prometheus text behind a MetricsSink interface (instrumentation in core, exposition swappable) — no OpenTelemetry SDK, the repo keeps its single dependency.
Deferred
Token / cost metrics (need adapter-level accounting). A push / OTLP MetricsSink is a future implementation of the same interface.

Phase 2 Identity & authorization ✓ done

Goal
A verified principal reaches the runtime and scopes every run; the allow / deny decision is left to an external policy layer that has live membership.
Landed
Identity. A TokenVerifier interface (verifier.go): staticToken (today's bearer check, the default) and trustedHeader — with --principal-header, the request must pass the bearer and then the principal is read from that header (set by the gateway authorizer). serve.go refuses --principal-header without --token (the header would be client-spoofable). httpServer.ownerOf keys run ownership on sha256("principal:"+p) when a principal is present, else the Phase-0 per-session hash — so run/list / run/status / run/resume / run/cancel / run/logs isolate per principal, and a non-owner gets the same -32602 as a nonexistent runId. CheckpointStore.WriteOwner persists a principal-owned run's owner to <runId>/owner, so after a restart reconstructRun hands it back only to that principal. Legible to a policy engine. POST /mcp/<method> thin wrappers (/mcp/run/resume, …) run the identical dispatch as POST /mcp; the body's method stays authoritative, a path/body mismatch is -32600. An Istio AuthorizationPolicy / API Gateway route / WAF rule then matches run/resume without parsing JSON-RPC.
Not in the language
No approvers: list. “Who may resume / approve” is dynamic policy (on-call rotation, IdP groups) and belongs to Istio / OPA / the gateway authorizer, not a versioned .mh file. Added: context.principal only — read-only, the verified caller identity of the current leg (starter or resumer), for a workflow to record who approved as audit data.
Deferred
JWKS / JWT verification (re-opens the dependency question; only needed with no gateway authenticating) and an --authz-endpoint OPA-style webhook — future TokenVerifier mode / flag.
Single pod
unchanged — default verifier is the static token; with no verifier there is no principal, and ownership falls back to the Phase-0 session hash. Full gate green (incl. -race), smoke against sample/cloud.
Gaps
3 (P0) · 10 (P1) · 12 (P2)

Phase 4 Self-limiting steps: the timeout clause ✓ done

Goal
A runaway or orphaned run self-terminates on whatever pod holds it — no cross-pod coordination — so the terminal state is visible everywhere from the shared store.
Direction change
The original Phase 4 (distributed live run registry, lease-based ownership, cas/lease/subscribe store methods) was rejected as wrong-layer. Instead the workflow author declares the ceiling in the .mh: step Build timeout 3m { … }, and the same clause on a parallel group bounds the whole barrier.
Changes
Grammar: an optional ( 'timeout' @Duration )? on ast.Step / ast.ParallelGroup (no new lexer token). runtime.Pipeline.StepTimeouts carries it; runner.go's execStage wraps that one step's context with context.WithTimeout, so every blocking call it makes is aborted on expiry. The step then fails like an explicit fail() — wrapping runtime.ErrStepTimeout, routed through saveCancelCheckpoint — so a checkpoint block keeps it resumable, with a fresh budget each attempt (the deadline is never persisted). mhl lint rejects a non-positive value.
Single pod
unchanged — a pipeline with no timeout clause is byte-for-byte as before.
Gaps
a purely non-blocking runaway is still bounded by max_iterations, not this

Language core vs. external extension

The dividing test has three answers, not two. Trust boundaries (who a caller is) and process lifecycle stay in core. Swappable I/O and vendor glue become extensions. Dynamic policy (may this caller do this, given today's on-call and IdP groups) leaves the runtime entirely — it lives in the mesh / an authorizer. Anything that would otherwise be a static list in a versioned .mh file is a smell.

The store extension, concretely

Kind store, one declaration per backend, discovered in the serve directory the same way workflows are. Sketch of the manifest and the call the adapter makes on every checkpoint:

// extension.json  (mhl-store-dynamodb)
{
  "id": "com.acme.mhl-store-dynamodb",
  "version": "0.1.0",
  "api_version": "1",
  "executable": "bin/store-dynamodb",
  "declarations_file": "declarations.json",
  "permissions": {
    "network": ["dynamodb.us-east-1.amazonaws.com"],
    "secrets": ["env(\"AWS_ROLE_ARN\")", "env(\"AWS_WEB_IDENTITY_TOKEN_FILE\")"]
  }
}

// .mh in the serve dir
extension store Backend {
  table:  "mhl-serve-state"
  region: "us-east-1"
}

// adapter -> Instance.Call on each OnStep / checkpoint write
call { declaration: Backend, operation: "cas",
       named_args: { key: "run//checkpoint", expect: , value:  } }

Open protocol questions to settle in Phase 3, all small and additive:

  • Server-lifetime processes. The child must outlive a run and restart with backoff instead of failing after three crashes. A manifest flag ("lifetime": "server") or a serve-side policy.
  • Hot-path cost. A pipe round-trip per checkpoint step is the concern. Benchmark first; mitigate with a write-through cache in the adapter (extension is the source of truth, reads are served locally) and batched flushes.
  • Watch. Cross-pod cancel and live status want push. Ship poll-only in v1; add a subscribe / event shape if polling latency hurts.
  • IRSA vs. “no ambient environment.” The AWS SDK in the extension wants AWS_WEB_IDENTITY_TOKEN_FILE / AWS_ROLE_ARN. Pass them through the manifest env allowlist, or add a host capability that mints them. Decide before writing the DynamoDB backend.
  • Distribution in EKS. Extensions are sha256-pinned and vendored under .mhl/extensions/. In a container that means baking them into the image or an init container — document it; there is no runtime download.
