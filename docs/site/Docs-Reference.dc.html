01Programs and modules

Executable

A program is a sequence of top-level declarations. Mark a declaration export to publish it, and import { ... } from "file.mh" to bring named declarations in from another file, optionally under a local alias. import is the only cross-file mechanism.

TWO-FILE EXAMPLE

shared.mh
export agent Echo {
    command: "echo"
    args: ["${prompt}"]
}

export prompt Greeting(name: string) {
    "Hello, ${name}!"
}
main.mh
import {Echo, Greeting as Hello}
    from "shared.mh"

pipeline Welcome {
    input name: string
    step Run {
        log(Echo.run(
            prompt: Hello(name: name)
        ))
    }
}
FormSyntaxWhen to use it
Exportexport prompt Name(...) { ... }Make a declaration reusable.
Import namesimport {A, B} from "file.mh"Bring in explicit contracts only.
Local aliasimport {LongName as Short} from "file.mh"Avoid collisions and improve readability.
Whole fileimport "file.mh"Merge every declaration, exported or not — see splitting a partial pipeline/workflow across files.
NOTE

import merges the target file's declarations into the program's flat namespace (transitively — an imported file's own imports come along), so a name resolves the same however it arrived. There is no namespace-qualified import. The brace-less import "file.mh" form skips the per-name export check entirely (there is no name list to check it against) and merges everything the file declares — mainly useful for a partial fragment, which has no reason to individually name and export itself.

02Syntax and types

Executable

MHL uses blocks, does not require semicolons, and allows object fields to be separated by commas or line breaks. Comments start with //.

NUMBERS & DURATIONS

A number is digits with an optional single decimal point (3, 0.2) — it carries no type suffix. A duration is an integer followed by a unit: ms, s, m, h, d (45s, 7d). A digit run glued directly to letters that is not a valid duration (10.0d, 1e5, 5days) is a parse error, not a number followed by a name. A string literal is always a string — even when its content is exactly an operator, so ["a","b"].join("-") is fine. duration is a literal form, not a declarable type: it is accepted only where an operation or a config field expects one (timeout:, ttl:, time.add, a step's timeout clause). Annotating a parameter : duration fails at run time with unrecognized type.

TYPE ALIASES

type Name = <type> names a type expression so a repeated or verbose shape is written once. An alias is only a spelling — it resolves to exactly the type its target denotes, adds no distinct type, and is usable anywhere a : type annotation is (inputs, parameters, returns, shape fields). Aliases may reference other aliases. A cycle, a duplicate name, an unknown target, or a name that shadows a builtin keyword is a static error (mhl lint).

type Slug      = string
type Ids       = string[]
type Violation = { code: string, severity: string }

tool Report {
    add(slug: Slug, issues: Violation[]): Ids -> issues.map((v) -> v.code)
}

ENUMS

enum Name { A, B, C } declares a closed set of named constants. A value is produced only by qualified access — Name.A — and at run time it is a distinct tagged value, not a string: Status.Draft == "Draft" is false, type_of(Status.Draft) is "enum", and "${Status.Draft}" / json.stringify render the bare variant (Draft). : Name is a type annotation like any other. A match over an enum value is checked for exhaustiveness by mhl lint.

enum Status { Draft, Published, Archived }

pipeline Publish {
    input status: Status
    step Decide {
        var note = match status {
            Status.Draft     -> "hold"
            Status.Published  -> "ship"
            Status.Archived   -> "skip"
        }
        log(note)
    }
}
ENUM INPUTS

An input typed with a declared enum — input status: Status above — closes its value set the same way in the inputSchema exposed via mhl serve mcp/a2a's tools/list: it renders as {"type": "string", "enum": ["Draft", "Published", "Archived"]}, not a bare {"type": "string"} — so a caller (or a client's own form/UI generated from the schema) sees the closed set of legal values up front instead of discovering it by trial and error.

03Expressions and collections

Executable

Expressions produce values. They compose inside variables, arguments, properties, conditions, returns, and string interpolation.

PRECEDENCE — LOWEST TO HIGHEST

??→||→&&→== !=→< > <= >=→+ -→* / %→! -→. ?. () []
var ready = retries < 3 && files.size() > 0
var label = if (ready) "ready" else "blocked"
var total = price * quantity + shipping
var dynamic = record[field_name]
var slice = numbers[1..^1] // index 1 through one before the end
var text = "${label}: ${total}"

// `?.` reads through null, a non-object, or a missing field without raising;
// `?.[key]` is the same with a dynamic key; `??` supplies a default only
// when the left side is null.
var target = metric?.target?.trim() ?? ""
var retries = config?.retries ?? 3       // 0 stays 0 — only null is replaced
var field  = record?.[name] ?? null      // no `is_object(record)` guard needed

MATCH

match is a multi-way branch in expression position. Arms are tried top to bottom; the first whose pattern is deep-equal to the subject (the same comparison == uses) wins, or the _ wildcard. A pattern is an Enum.Variant or a bool/number/string literal. A match over an enum or bool with no _ arm must cover every case — mhl lint flags a missing one; any other subject relies on a runtime error if nothing matches.

var tier = match http_status {
    200 -> "ok"
    404 -> "missing"
    _   -> "error"
}

RUNTIME TYPES

type_of(x) returns a kind string ("string", "number", "bool", "array", "object", "null", …); is_string, is_number, is_bool, is_array, is_object, is_null are the per-kind predicates. Pair them with ?. to branch on a dynamic field's shape.

NAMEOF

nameof(Name) takes a bare declared name — an agent, router, memory, tool, prompt, skill, pipeline/workflow, extension, type, or enum — and returns it as a string, validated to exist. Prefer it over a string literal anywhere a declared name is needed as text (the router's select hook is the main case): a typo in nameof(Billing) is a mhl lint error, and the identifier is a real reference an editor's "go to definition" follows.

DETERMINISTIC SELECTION EXAMPLE

var passed_ids = [10]
var features = [
    {id: 20, status: "pending", priority: 2, depends_on: [10]},
    {id: 30, status: "pending", priority: 1, depends_on: [99]},
    {id: 40, status: "pending", priority: 3, depends_on: []}
]

var ready = features
    .filter((f) -> f.status == "pending")
    .filter((f) -> f.depends_on
        .filter((d) -> !passed_ids.contains(d))
        .is_empty())
    .sort_by((f) -> f.priority)

var next = ready.find((f) -> f.id == 20)
IMMUTABLE RESULTS

filter(), map(), sort_by(), append(), unique(), concatenation, and slices return new arrays. To accumulate into a list, reassign — acc = acc.append(x) or acc += [x]. Assigning to items[index] or object[key] mutates the original collection.

05agent

Executable

Declares an AI backend callable through .run(prompt: ...). The runtime supports local CLI processes and models served by Ollama.

CLI AGENT

agent Claude {
    engine: "cli/claude-code"
    command: "claude"
    args: [
        "-p", "${prompt}",
        "--output-format", "json",
        "--json-schema", "${schema}"
    ]
    retry: {
        max_attempts: 3
        delay: 2s
        retry_on: [500, 503, "timeout", "rate_limit"]
    }
    cache: { ttl: 10m, storage: "disk" }
    rate_limit: { requests_per_minute: 20, concurrency: 2 }
}

CLI AGENT — PROMPT VIA STDIN

// Codex CLI reads its prompt from stdin when the positional argument is
// "-" — keeping an unboundedly large prompt (e.g. concatenated source

// per Codex's own CLI, not inline JSON — `stdin:` only removes the prompt

agent Codex {
    engine: "cli/codex"
    command: "codex"

agent Claude {

ALPHA

retry.backoff, cache.strategy and rate_limit.on_exceeded each accept exactly one value today — "exponential", "exact" and "queue" respectively. Any other value is a build-time error at both mhl lint and mhl run. Fields the older docs may still show (api_key, timeout, system_instructions) are not read and are now a lint error.

RETRY

The exponential backoff carries full jitter (each wait is a uniform pick in [0, delay·2ⁿ]) and is capped at 30s per wait — the cap applies from the very first wait, so a delay larger than it is trimmed immediately rather than sleeping once at the full amount — so a large max_attempts never grows an unbounded sleep. The wait is governed by the run's context: a run-level cancel, a timeout clause, or a served run/cancel aborts a retry that is only sleeping, rather than blocking until the delay elapses. A cancelled or deadline-exceeded call is never retried, whatever retry_on says; the caller then sees the last real failure, not the cancellation.

WINDOWS

A prompt built from unbounded source content (an entire wiki, a full document) can push args:'s "${prompt}" past Windows's ~32,767-character command-line ceiling with no warning until mhl run fails on that platform specifically — CreateProcess refuses to start the child process at all, and the error surfaces as raw OS text ("The filename or extension is too long") with no hint the real cause is argv size. macOS/Linux have no equivalent limit worth guarding (their execve ARG_MAX is 1-2MB), so this only bites on Windows, and typically only in production — a development machine on macOS/Linux runs the exact same pipeline without error. Move the large piece to stdin: instead of args: to sidestep it entirely.

PROMPT INJECTION

Some backends apply their own prompt-injection heuristics to stdin: content, separately from anything mhl does — the Claude Code CLI in particular can refuse to respond at all when piped stdin content reads like an instruction rather than reference material. Confirmed against the real CLI: piping "THE SECRET WORD IS BANANA" alongside a -p instruction that referenced it got refused outright ("This appears to be a prompt injection attempt..."), while piping the same kind of content framed as a document to summarize (no embedded imperative) was answered normally. When an agent's args: carries a fixed instruction and stdin: carries separate reference material to analyze (the Claude pattern above) — as opposed to a backend like Codex's -, which is designed to read the whole instruction from stdin — keep that material read as data, not phrased as a command the model should follow.

!
Do not place secrets in args or stdin.

Prefer environment variables resolved by the invoked process. To preserve spaces and special characters in prompts, keep "${prompt}" as one complete array element in args:, or route it through stdin: instead.

BEFORE / AFTER HOOKS

An agent is a single-shot CLI process — it cannot decide mid-generation to call a tool or an MCP server. before/after are how the pipeline does that calling on the agent's behalf: real values, fetched before the prompt exists, not a hope the model reads and acts on an instruction.

agent Reviewer {
    command: "claude"
    args: ["-p", "${prompt}"]

    before: () -> {
        return {
            issue: GitHub.call("get_issue", { number: 42 }),
            diff: execution.git_diff()
        }
    }
    after: () -> {
        log("review is ${result.size()} characters")
    }
}

var review = Reviewer.run(
    prompt: "Issue: ${issue}\nDiff: ${diff}\nWrite a review."
)
  • A hook body is an ordinary expression scope: it calls declared tool/extension/agent names, native ops (http, cmd, …) and mem the same way a step does. Both hooks take no parameters — a leftover (mcp, tools) -> is an error.
  • Reads the caller's variables; writes never come back. Like any lambda, a hook closes over the scope that issued the .run(...) call — a step's, or an intermediary tool method's — as a one-time snapshot, not a live view: the body sees each captured variable's value as it stood when the hook started, but a bare name = ... assignment inside the body is accepted with no error and simply never reaches the caller's real variable, at any call depth — even called directly from a step, with no tool in between. A hook's only way to actually hand data back is its own return value (below), or an external effect it performs itself (a tool/extension call, mem).
  • before's returned object's fields become real "${...}" bindings available to that call's prompt:/schema: arguments — the one channel a hook has for handing structured data back to its caller.
  • after runs once, against whichever leg — the primary agent or a successful fallback — produced the final response, with it bound in the body as result. Its return MUST be a string or nothing: a non-null string replaces the response, no return (or an explicit null) passes it through unchanged, and any other type — an object included — raises "<Agent>.after must return a string (or nothing), got <type>". Unlike before, after cannot hand back structured data through its return value.
REAL CALLS

before/after execute real calls through mhl itself — the model never has to cooperate, and there is no separate declarative tool-scope list on the agent. When an agent needs a tool or an extension, call it from before and pass the result in through the prompt.

SKILLS

A skill (§08) is a reusable instruction package loaded from a Markdown file. skills: on the agent is an allow-list; run(skills: [...]) selects a subset of it, in call order; system_prompt is the only place that selection actually reaches the outgoing request.

skill CodeReview from "code-review.md"
skill SecurityReview from "security-review.md"

agent Reviewer {
    command: "claude"
    args: ["-p", "${prompt}"]
    skills: [CodeReview, SecurityReview]

    system_prompt: (skills, prompt) -> {
        var instructions = ""
        for (var s in skills) {
            instructions = instructions + "## " + s.frontmatter.name + "\n" + s.content + "\n\n"
        }
        return instructions + prompt
    }
}

var review = Reviewer.run(
    skills: [CodeReview, SecurityReview],
    prompt: "Review this diff."
)
  • A call that never writes skills: at all never invokes system_prompt — the request sent is exactly what prompt: resolves to, identical to an agent with no skills feature in play, even on an agent that declares both skills: and system_prompt.
  • system_prompt's first parameter is a list of {name, frontmatter, content} objects, one per selected skill, in call order. name is the skill's MHL declaration identifier — the same string nameof(CodeReview) resolves to, so a hook can compare by identity (s.name == nameof(CodeReview)) instead of a free-floating string. frontmatter is the parsed frontmatter block (frontmatter.name/frontmatter["name"] both work); content is the Markdown body with the frontmatter stripped out.
  • Selecting a skill the agent didn't permit, repeating one, or naming one that isn't declared all fail before any model call — in both mhl lint and mhl run.
  • Retry and fallback reuse the exact same already-composed prompt: system_prompt runs once, before the primary attempt, never per retry and never again for a fallback leg.

06router

Executable

Declares a decision layer over a set of already-declared agents and exposes one method, .delegate(prompt: ...), that picks which one should handle a given prompt and runs it — the same call shape as agent.run(...), with routing built in. The LLM decision call is optional: a router that declares only select is a purely deterministic router.

HYBRID DECISION

agent Billing {
    command: "claude" args: ["-p", "${prompt}"]
    description: "Handles invoices, billing questions, and refunds"
}
agent Support {
    command: "claude" args: ["-p", "${prompt}"]
    description: "Handles account access and technical issues"
}
agent Judge { engine: "cli/claude-code" command: "claude" args: ["-p", "${prompt}"] }

router Frontdesk {
    agents: [Billing, Support]

    // Tried first: a deterministic hook over the prompt text. A match
    // skips the LLM decision call entirely. nameof(Billing) — not the
    // string literal "Billing" — so a typo here is caught by mhl lint.
    select: (prompt) -> {
        if (prompt.contains("invoice")) { return nameof(Billing) }
        if (prompt.contains("refund")) { return nameof(Billing) }
        return null
    }

    // Used only when select is absent or returns nothing that names a
    // declared agent: Judge is an ordinary, independently declared agent
    // — nothing about its call configuration is duplicated on the
    // router — sent one "pick one of these agents" decision call built
    // from the prompt already passed to .delegate(...).
    decider: Judge
}

var reply = Frontdesk.delegate(prompt: "My invoice is wrong.")

PURELY DETERMINISTIC — NO LLM CALL AT ALL

router Frontdesk {
    agents: [Billing, Support]

    // No decider declared at all: there is no decision call to cascade
    // to, so select alone must be exhaustive.
    select: (prompt) -> {

DESCRIPTION

The decision prompt sent to decider lists each of agents' bare names. When an agent declares its own optional description property, that text is appended right after its name — no separate per-agent description list is declared on the router itself. An agent with no description still contributes its bare name.

DELEGATE

.delegate(prompt: ..., schema?: ...) resolves the agent to run — via select, else the decision call — then runs that agent with the same arguments the caller passed, returning its response unchanged. The chosen agent's own retry/cache/rate_limit/fallback/before/after all apply exactly as they would for a direct .run(...) call — and so does the decider's, for the decision call itself.

OPTIONAL LLM CASCADE

The decision call is opt-in, not implied by declaring a router: it only exists when decider is declared. A router with neither a decider nor a select hook is rejected by mhl lint — it could never resolve an agent. A router with only select is accepted; if that hook ever misses at run time (with no decider to fall back to), .delegate() fails with a clear "no decider is configured" error instead of silently trying to run one.

NAMEOF

nameof(Name) returns a declared top-level name (agent, router, memory, tool, prompt, skill, pipeline/workflow, extension, type, enum) as a string, validated to exist — the argument must be a bare identifier, not a string or an expression. Returning nameof(Billing) from select instead of the string literal "Billing" means a typo is a mhl lint error, and "go to definition" on Billing in an editor follows it to the real agent declaration. A non-null select return that still names no declared agent — a plain string typo, or a stale rename — always fails .delegate() immediately, listing the real agent names; it is never silently treated as "select declined to decide".

ALPHA

An agents: entry naming an undeclared agent, or a decision call whose answer matches none of them, is also an error — at mhl lint time for the former, at .delegate() call time for the latter.

10tool and native operations

Executable

A tool creates a small, reusable API over native operations. Declare const or var in the tool body for values shared by its methods during a call. Methods take positional arguments, may declare types, and use either an expression body or a statement block.

DEFAULT ARGUMENTS

A method or lambda parameter may end with = expression — write(path: string, mode: string = "0644") — supplying a value when the caller omits that argument. Positional parameters bind left to right, so a default may read an earlier parameter (close: string = open) but a non-defaulted parameter may not follow a defaulted one (mhl lint flags it). Each default is evaluated in the callee's own scope, once per call that omits it.

SELF

Inside one method, self.other_method(...) calls a sibling method of the same tool — useful for composing small, private helpers into a public one (changed_go_files() above could read self.git_root(), say). It resolves to this tool regardless of what else is declared elsewhere, so renaming the tool never breaks its own internal calls. self means something different — a pipeline/workflow's own state — inside a step; see SELF INSIDE A STEP. Using either self. form in the wrong place (a tool method calling self.some_property, or a step outside any pipeline) is a mhl lint error, not a silent no-op.

  • transport: "http" uses url and headers; each call is a fresh, independent request.
  • env("NAME") resolves a credential only when needed and keeps it out of source.
  • .call(toolName, arguments) issues a JSON-RPC tools/call; .list_tools() issues tools/list; .discover() issues server/discover (supported versions/capabilities/identity), or, against a handshake server, returns the initialize result's identity instead.

  • In "auto" mode the stateless 2026-07-28 form is tried first; if the server rejects it with a protocol-incompatibility error (JSON-RPC -32602/-32600, or HTTP 400) the call is retried over the standard initialize / notifications/initialized handshake (advertising 2025-11-25, _meta dropped, Mcp-Session-Id threaded through), letting the server negotiate the version down.   • A server response with resultType: "input_required" (Multi Round-Trip Requests — the server wants elicitation/sampling input) is rejected with a clear error; this client cannot gather and resubmit that input.
PROTOCOL

A stateless 2026-07-28 call keeps no session between calls — each is fully independent, self-identifying with its protocol version, capabilities, and a {name: "mhl", version} clientInfo. "auto" (the default) may fall back to a short initialize/notifications/initialized handshake for a server on the 2025-11-25 or 2025-06-18 revisions; that handshake session lives only for the one call. A credential that fails to resolve aborts the call instead of sending a request with an empty header.

step Gate {
    if (!approved) pause("review " + artifact)
    goto match artifact {
        "brief" -> BriefCommit

goto match evaluates artifact once and selects the first matching arm. To reuse that table, declare route Generate(artifact: string) { ... } in the workflow and call it with goto Generate(artifact) from any step. A route has one typed parameter and static step destinations; mhl lint checks its name, arity, patterns, and targets. It transfers control directly rather than returning a string. Expression nameof(BriefGenerate) cannot name a workflow step because that builtin checks top-level declarations. On --resume, a paused gate runs again with updated inputs and selects the route then. See sample/syntax/pipeline_vs_workflow/goto_match_artifact_review.mh.

SPLITTING ACROSS FILES

A large workflow — many artifact types, each its own Generate/Commit pair — can outgrow one file. partial splits the declaration, not the pipeline: every fragment sharing a name and the same pipeline/workflow keyword is combined into one declaration before it ever runs, exactly like C#'s partial class. A fragment is pulled in with the bare, brace-less form of import — import "file.mh" — which merges every declaration in that file, not just named/exported ones; that's what lets a fragment join without itself being exported. Because steps and pipeline-scoped vars are looked up by name, a goto in one fragment reaches a step declared in another with no extra wiring.

discovery.mh
import "discovery.brief.mh"

partial workflow Discovery {
    var pending_data = null

    entry step Dispatch {
        goto BriefGenerate
    }
}
discovery.brief.mh
partial workflow Discovery {
    step BriefGenerate {
        pending_data = { title: "brief" }
        log(pending_data)
    }
}

Because a pipeline otherwise starts at its first physically declared step, and "first" stops meaning anything once steps arrive from more than one file, a partial declaration must mark its real starting point explicitly: exactly one step, anywhere among its fragments, carries the entry keyword — entry step Dispatch { ... } above. entry is rejected outside a partial declaration, where the first step is unambiguous already.

SELF INSIDE A STEP

Inside a step, self.name reads or writes a declared input/var/mem of that step's own pipeline — self.pending_data = json.parse(raw) reads exactly like pending_data = json.parse(raw) does today, and both keep working side by side. The difference is what self. makes visible at the point of use: a bare name gives no hint whether it's this step's own local var or shared pipeline state declared somewhere else entirely (in a partial pipeline, possibly a completely different file) — self. always means the latter, unambiguously, and it's what an editor's completion can act on: typing self. inside a step lists every input/var/mem the pipeline declares, gathered across every merged partial fragment, not just the file currently open. It also settles a real edge case cleanly: if a step-local var happens to share a name with a pipeline-level one, the bare name reads the local shadow (as it always has) while self.name always reaches past it to the pipeline's own binding.

USE COMPLETE() FOR A CONVERGENCE STEP

A step with no goto at the end of its body isn't a problem by itself — mhl's execution model defaults to sequential fallthrough everywhere (a plain pipeline has no goto at all), so it's completely normal for a step to just flow into the next one physically declared after it. It only becomes a footgun for one specific kind of step: a shared convergence point every branch gotos to, meant to end the run — its safety depended entirely on happening to be the physically last step, which stops being obvious once a workflow is split across files (the merged order follows import order, not any one file's own layout). Give that step a body of complete() instead of leaving it empty: step Done { complete() } ends the run in the normal "completed" state right there, regardless of where the merge puts it — no more reasoning about which fragment gets imported last. This is not a hypothetical: an empty convergence step silently ended up mid-plan after a real split, and a completed run continued into the next artifact's generation step, firing an unwanted LLM call — complete() exists specifically so that can't happen again, not just so mhl lint catches it after the fact (which it still does — see FALLTHROUGH ACROSS FRAGMENTS below — for a step that hasn't been converted yet).

FALLTHROUGH ACROSS FRAGMENTS

mhl lint checks one specific seam: a fragment's own last step, when another fragment is still merged in after it, must end in an unconditional goto/goto match/fail(...)/pause(...)/complete()/break (or a trailing if/else where both branches do) — otherwise it silently falls through into a step in a different file. A step that isn't its fragment's last member is never checked — reordering steps inside one file is exactly as visible as it always was, and sequential fallthrough there is completely normal, not flagged. Prefer fixing a real terminal step with complete() (above) over just satisfying this check with a goto to nowhere useful.

LONE FRAGMENT

A fragment file linted or edited on its own — its siblings not pulled in by anything in that file — stays quiet about being incomplete, since that's the expected shape, not a bug in the fragment: a missing entry step, a goto/route target it can't see, and a step assigning to a pipeline-scoped var declared only in a sibling are all withheld the same way, and for the same reason — this one file genuinely cannot tell "the rest is elsewhere" from "actually wrong." Once a whole-file import somewhere has genuinely merged more than one fragment together, all of that comes back: a still-missing entry, a target that still doesn't resolve, a variable that's still nowhere declared. Either way, mhl run (via runtime.FindPipeline, and a real undefined-variable error at the step that reads it) always catches a truly broken pipeline the moment something tries to actually run the assembled result, lint or no lint. A directory-wide scan (mhl serve mcp <dir>, mhl test <dir>) skips registering an incomplete fragment rather than failing the whole directory over it.

CHECKPOINT

The checkpoint: { enabled, strategy, storage, ttl } block is optional. Every pipeline/workflow is projected with enabled: true, strategy: "per_step" unless it says otherwise, so an interrupted run is always resumable with mhl run --resume / run/resume and a completed run clears its own state. Declare the block only to override a field — checkpoint: { ttl: 30d } keeps the default strategy and just changes retention; checkpoint: { enabled: false } turns checkpointing off for a workflow whose steps aren't safe to half-replay. strategy has one value today ("per_step") and storage one ("file").

SESSIONS

Every run gets its own directory .mhl/state/<session-id>/, so two concurrent runs of the same pipeline never clobber each other's checkpoint. Each run prints a session: <id> line; a bare --resume follows the most recent one (via a .mhl/state/<pipeline>.latest pointer), and --session <id> pins an exact one. Abandoned session directories past their TTL are swept automatically at the start of a later run.

DEFINITION BINDING

Every checkpoint records a digest of the pipeline it was written for — that pipeline's own body plus the shared declarations it can reference (agents, tools, prompts, memory, extensions, types, imports); comments and formatting are excluded, and editing a sibling pipeline or a test block in the same file does not affect it. A --resume whose current digest differs is refused with a definition-mismatch error rather than splicing the saved variable state into changed control flow: restore the original definition, re-run without --resume, or — if you know the edit is safe to resume through — pass --resume --force to downgrade the check to a warning. A checkpoint written by an older mhl that predates this field still resumes.

WHAT PERSISTS

Checkpoint state is JSON. A pipeline-scoped var survives --resume only if it holds a string, number, bool, null, or an array/object of those; a resolved secret is stored as its re-resolvable reference (env("…")) and re-read on resume. Assigning something JSON cannot represent — a closure, a handle — to a pipeline-scoped var fails the run at the next checkpoint with a clear message rather than being silently dropped to {}; keep closures in step-local vars (which never cross a checkpoint), or set checkpoint: { enabled: false }.

CREDENTIAL REFERENCES

Explicit credential resolution protects the exact nonempty value, including short or numeric strings and significant whitespace. Ordinary env() reads still use name/value heuristics; they do not declare every environment value a credential. Whole secret values with one known reference can be rehydrated; embedded or reference-free secrets are masked. If distinct references resolve to identical content in the same runtime process, string state cannot distinguish their origin: checkpoints retain an ambiguity marker and resume fails explicitly. Start a new run with distinct credentials instead of selecting either reference silently. Registration is process-wide, so an explicitly registered short value also masks matching text elsewhere in that process.

SIDE EFFECTS

A checkpoint records progress between steps, not the external effects a step performed. If a step creates a ticket, POSTs to an API, or runs a cmd, then fails — or the process dies — before its checkpoint is written, --resume re-runs that whole step and repeats the effect; a pause re-enters its step the same way, and a failed parallel branch re-runs alongside its already-completed siblings. mhl gives at-least-once execution per step, never exactly-once for an external system. Make a step that mutates the outside world idempotent: pass your own idempotency key to the API, check-then-act, or split prepare / approve / apply into separate steps so only the final, cheap apply can repeat. Give a repeated agent call a cache.

pipeline BuildCounter {
    context: {
        source: "latest"     // or "session:<id>"; default "latest"

    var build = 1

    step Report {
        log.info("session ${context.session_id}, resumed=${context.resumed}")

CONTEXT

context is read-only and always available in every pipeline/workflow step — no declaration needed. context.session_id, context.started_at and context.resumed describe the current run; context.principal is the verified caller identity when the run was started through mhl serve mcp --http with a token verifier (--principal-header), and "" otherwise (a plain mhl run, or no verifier) — use it to record who triggered or approved a run, not to authorize. The context: { source, require } block is only needed for context.vars — the variable state the previous completed run of this pipeline finished with (persisted as result.json in that run's session directory). Without the block context.vars is {}; with it, it is still empty until a run has completed once — guard with context.vars.keys().contains(...).

workflow PublishRelease {

    }
}
OUTPUT

The optional output: { name: expr, … } block is the run's result contract. With it declared, a mhl run caller — and every mhl serve mcp / serve a2a client — receives only these keys, each evaluated against the final variable state (so a key can be renamed, computed, or dropped). Without it, the legacy behaviour returns every non-internal var. The mapping does not change what a later run's context: reads back — that still sees the full variable state. The value must be an object mapping; anything else fails the run.

OUTPUT & PAUSE

The mapping is evaluated once, only when the run finishes (a completion or a break). A run parked by pause(...) skips it — its expressions may read a var that step has not reached — and the suspension response returns the partial state; the run/resume (or mhl run --resume) that completes the run produces the real projection. The result is not checkpointed, so a resume re-evaluates it, and a mapping expression observes the run's cancellation/deadline — keep side effects out of it.

LOOP WITH AN EXPLICIT STOP

loop pipeline PollBuild {
    mem status = "pending"
    mem checks = 0

    repeat: {
        stop_when: status == "passed"
        max_iterations: 20
    }

    step Check {
        checks = checks + 1
        var response = http.post(
            url: "https://ci.example.com/status",
            body: {attempt: checks}
        )
        status = json.parse(response.body).status
        if (status == "failed") break "build failed"

}
MAX CLAUSE

When a fixed iteration ceiling is the whole repeat policy — no stop_when — write it as a max <N> header clause instead of a one-field repeat block: loop workflow Refine max 3 { … } is exactly repeat: { max_iterations: 3 }. The word max is reserved only in that position (after the declaration name), so a pipeline may still be named max. Declaring both the clause and an explicit repeat max_iterations is a mhl lint error — the repeat block wins — and max without the leading loop keyword is flagged as inert.

CONCURRENT SUB-AGENTS IN A STEP

pipeline Review {
    input diff: string
    input changed_files: string[]

    spawn: { max_concurrency: 4 }   // run-wide ceiling; default 4

    step Analyze {
        spawn rev   = Reviewer.run(prompt: "review:\n${diff}")
        spawn tests = Tester.run(prompt: "run the tests for:\n${diff}")
        spawn sec   = Security.run(prompt: "security pass:\n${diff}")

        wait rev, tests, sec timeout: 90s        // wait-all, fail-fast
        // wait any rev, tests, sec              // first success, cancels the rest
        // wait 2 of rev, tests, sec             // first N successes (quorum)
        // wait rev, tests on_error: "collect"   // never fails the step; read .ok / .error

        log(rev.result)
        if (!tests.ok) log("tests failed: ${tests.error}")
    }

    step FanOut {
        // one spawn per element: `item` is bound while each call's arguments
        // are built, so every prompt differs. `reviews` is an array of task
        // handles — `wait` joins it as a group; it indexes and iterates.
        spawn reviews = Reviewer.run(prompt: "review file ${item}") for item in changed_files
        wait reviews timeout: 90s                // or `wait any reviews` / `wait 2 of reviews`
        for (var r in reviews) log("${r.status}: ${r.result}")
    }
}

LIMITS

For loops, always prefer an observable stop_when plus max_iterations as a safety ceiling. Step-local variables are not visible to stop_when; use mem or memory.

TIMEOUT

A step <Name> timeout <duration> { … } clause caps how long that step may run — step Build timeout 3m { … }. The runtime wraps the step's context with that deadline, so every blocking call it makes (an agent, http, cmd, an extension) is aborted when it elapses; the step then fails exactly as an explicit fail() would, so --resume / run/resume can still re-enter the step (unless the workflow set checkpoint: { enabled: false }) — with a fresh budget (the duration is per attempt, never persisted). The same clause on a parallel <Name> timeout <duration> { … } group bounds the whole barrier and cancels every still-running branch; a branch may also carry its own timeout, and the earliest deadline wins. A purely non-blocking runaway (a spinning while) is still bounded by max_iterations / the interpreter's loop cap, not by this.

SPAWN

spawn/wait are step-scoped: any handle not joined by a wait is joined automatically when the step ends, so nothing runs across a checkpoint. If the process dies mid-step, --resume re-runs the whole step and re-issues every spawn — keep them idempotent (or give the agent a cache). A spawned agent cannot itself spawn, and an agent's log: file is ignored under spawn (its output goes to the step log instead). The fan-out form spawn xs = Agent.run(...) for item in <array> starts one background call per element with item bound while that call's arguments are evaluated, and binds xs to an array of handles in element order — index it (xs[0].result), iterate it (for (var h in xs) …), take its .size(), and wait xs / wait any xs / wait N of xs. A non-array iterable is a runtime error; an empty array binds an empty handle array that a plain wait no-ops on. The run-wide max_concurrency still bounds how many are in flight, so fanning out over a large collection is safe.

PARALLEL

A parallel <Name> { … } group runs its steps concurrently and joins them all before the pipeline advances — the step-level counterpart of spawn (which parallelises agent calls within one step). Each branch gets its own copy of the pipeline vars; on join, the writes are merged back, and a var two branches set to different values fails the run — so the outcome is deterministic. Branch output is buffered and printed in declared order. The group is atomic for checkpointing: a crash re-runs the whole group on --resume, so branch steps must stay idempotent. goto may not target a grouped step or be used from within one, and break may not be used from within one.

RUNNING A WORKFLOW FROM A TEST

Inside a describe block only, Name.run(inputs?: object) — where Name is a declared pipeline/workflow — runs its steps to completion (or to a break/pause/failure) in an isolated, throwaway sandbox and returns the outcome as an object instead of raising, so a test can assert on a workflow expected to fail exactly as easily as one expected to complete.

pipeline GuardedRetry {
    step Implement {
        var attempts = 4
        if (attempts > 3) break "too many attempts"
    }
    step Handoff { var done = true }
}

test guarded_retry_test {
    describe stops_after_too_many_attempts {
        var result = GuardedRetry.run()
        is_true(result.ok)
        are_equal(result.state, "broke")
        are_equal(result.break_reason, "too many attempts")
        are_equal(result.executed, ["Implement"])
    }
}

RAISES VS. REPORTS

fail()/break/pause(...) inside the workflow's own steps never raise — they land in the returned object. Only a problem with the call itself raises: a missing/mistyped required input, or a loop pipeline/loop workflow target (not supported yet). Calling .run() outside a describe block is refused — a run executing another synchronously mid-step has no defined interaction with checkpointing or context yet.
