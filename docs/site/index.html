A LANGUAGE FOR AI WORKFLOWS

You write the flow. AI does its part.

MHL is a programming language for orchestrating AI agents. Write workflows with branching, bounded loops, fan-out and human approval in a .mh file. Run it with a single command.

Get started with MHL→ Explore the code↘

One readable file. A dedicated runtime. The flow under your control.

mhrefine.mhAN MHL PROGRAM
agent Writer {
    command: "claude"
    args: ["-p", "${prompt}"]
}

loop workflow Refine max 3 {
    spawn: { max_concurrency: 2 }
    mem draft = "A first draft."
    mem feedback = ""

    step Improve timeout 45s {
        draft = Writer.run(
            prompt: "Improve: ${draft}\nFeedback: ${feedback}"
        )
    }
    step Review timeout 45s {
        var lenses = ["clarity", "accuracy"]
        spawn checks = Writer.run(
            prompt: "Review ${draft} for ${lens}."
        ) for lens in lenses
        wait checks timeout: 40s
        feedback = checks.map((c) -> c.result).join("\n")
        log(draft)
    }
}
$mhl run refine.mh

↳Up to 3 refinement rounds, with 2 concurrent reviews per round and feedback in the next iteration. Requires authenticated Claude CLI; makes real provider calls.

01 / WORKFLOWS, IN PRACTICE

Branching, limits and concurrency. In code.

Explore six complete programs: from control flow to fan-out, human approval and typed contracts. The examples below run locally, without model calls.

01.

Route the work. Choose the next step.

workflow supports explicit branches with goto match and reusable route tables. Each branch converges on Done; complete() finishes the run without falling through to another step.

workflow
An execution unit that can branch between steps.
route + goto
A typed routing table with statically checked destinations.
complete()
Ends the workflow in the completed state.

pipeline also supports loops and concurrency, but its steps follow declaration order: goto is reserved for workflow.

Explore in the playground↗
mhworkflow.mh
workflow CreateArtifact {
    input artifact: string = "brief"

    route Generate(kind: string) {
        "brief" -> Brief
        "adr" -> Adr
        _ -> fail("Unknown artifact: " + kind)
    }

    step Choose {
        goto Generate(artifact)
    }
    step Brief {
        log("brief ready")
        goto Done
    }
    step Adr {
        log("adr ready")
        goto Done
    }
    step Done { complete() }
}
$mhl run workflow.mh --input artifact=brief
EXPECTED OUTPUTbrief ready
02.

Iterate with a ceiling. Stop when ready.

loop workflow repeats the sequence of steps. max 3 caps full iterations; mem keeps state across rounds. This local example finishes on round 2 with break.

max 3
At most three full iterations; does not cap goto visits.
mem
Retains values between iterations, unlike var.
break
Ends the entire execution early.

For a state-based stop condition, use repeat: { stop_when: ..., max_iterations: 3 } instead of the max clause. The example uses a counter to demonstrate early termination without a model.

Explore in the playground↗
mhlimits.mh
loop workflow Refine max 3 {
    mem round = 0
    mem draft = "first draft"

    step Improve {
        round += 1
        draft = "${draft} / revision ${round}"
    }
    step Evaluate {
        log("round ${round}")
        if (round == 2) break "ready"
    }

    output: { rounds: round, text: draft }
}
$mhl run limits.mh
EXPECTED OUTPUTround 1 round 2
03.

One collection. Multiple agent calls.

spawn … for starts one call per item. The runtime limits calls in flight and wait joins their handles. Echo stands in for a model so this example runs locally.

spawn … for
One task handle per collection item.
max_concurrency
At most two agent calls in flight across the run.
wait
Wait for all tasks; any and N of select other policies.

wait any checks returns on the first success; wait 2 of checks waits for two successes. Both cancel remaining tasks: remove on_error: "collect" when using these policies. collect applies only to plain wait; inspect .ok and .error. Requires echo on PATH.

Explore in the playground↗
mhfanout.mh
agent Echo {
    command: "echo"
    args: ["${prompt}"]
}

workflow ReviewFiles {
    spawn: { max_concurrency: 2 }

    step FanOut timeout 5s {
        var files = ["api.go", "auth.go", "cli.go"]
        spawn checks = Echo.run(
            prompt: "check ${file}"
        ) for file in files
        wait checks timeout: 2s on_error: "collect"

        for (var check in checks) {
            if (check.ok) log(check.result)
            else log(check.error)
        }
    }
}
$mhl run fanout.mh
EXPECTED OUTPUTcheck api.go check auth.go check cli.go
04.

Parallelize whole steps, then merge.

parallel runs steps concurrently and waits at a barrier before Merge. This local example uses fixed values; each branch could call agents, HTTP or tools.

parallel
Concurrency between whole steps.
timeout 2s
A deadline for the entire group.
barrier
Branch writes merge before the next step.

spawn parallelizes agent calls inside one step; parallel parallelizes the steps themselves. Conflicting writes of different values to the same variable fail the run.

Explore in the playground↗
mhparallel.mh
workflow Enrich {
    var docs = ""
    var tests = ""

    parallel Gather timeout 2s {
        step Docs {
            docs = "docs ready"
        }
        step Tests {
            tests = "tests ready"
        }
    }

    step Merge {
        log("${docs}; ${tests}")
    }
}
$mhl run parallel.mh
EXPECTED OUTPUTdocs ready; tests ready
05.

Let a person decide. Resume from the gate.

pause saves a suspended run. Resume with the same session and updated input; Gate runs again and goto match chooses the next step. The example only logs; it does not publish anything.

pause()
Suspends execution, preserving its checkpoint.
--resume
Re-enters the paused step in the same session.
goto match
Branches to a declared step from the decision.

Checkpoints are enabled per step by default. Resuming re-executes the paused step: keep external effects idempotent and separate preparation, approval and application.

Explore in the playground↗
mhapproval.mh
workflow Approval {
    input approved: bool = false
    checkpoint: { ttl: 7d }

    step Gate {
        if (!approved) pause("Waiting for approval")
        goto match approved {
            true -> Publish
            _ -> fail("Approval required")
        }
    }
    step Publish {
        log("approved")
        complete()
    }
}
$mhl run approval.mh --session demo mhl run approval.mh --session demo --resume --input approved=true
EXPECTED BEHAVIORFirst run: paused After resume: approved
06.

Give the workflow a contract. Test it.

A typed signature defines inputs and results. A reusable prompt renders the greeting; output projects the public result. test runs the workflow in an isolated sandbox and checks its contract.

(req: In): Out
Input and output object types.
prompt
A reusable template with typed parameters.
test
Assertions over the real workflow result.

The projected result is checked at completion. When served over MCP, the input and output types are advertised as schemas for clients.

Explore in the playground↗
mhcontract.mh
type In = { name: string }
type Out = { message: string }

prompt Greeting(name: string) {
    "Hello, ${name}!"
}

workflow Greet(req: In): Out {
    var message = ""
    step Build {
        message = Greeting(name: req.name)
    }
    output: { message: message }
}

test greeting {
    describe returns_the_contract {
        var run = Greet.run(inputs: { name: "Ana" })
        is_true(run.ok)
        are_equal(run.output, { message: "Hello, Ana!" })
    }
}
$mhl run contract.mh --input name=Ana mhl test contract.mh

More ways to compose your workflow.

Agents, prompts and skills

Call model CLIs or APIs, compose prompts and select reusable Markdown instructions. Schemas describe structured agent outputs.

agent · prompt · skill · schema

Routing between agents

Select an agent through a deterministic rule. When select cannot decide, an optional decider can choose where to delegate.

router · select · decider · delegate

Composition across files

Split a workflow with partial, share modules and expose aliases with bound inputs. internal keeps the base flow out of entry points.

partial · import/export · alias · internal

Explicit state and memory

Use mem across iterations and memory for named KV, JSON or JSONL stores. Record audit data and read session context.

mem · memory · context · lifecycle hooks

Execution policies

Declare retry, cache and fallback on the agent. Combine step or group deadlines with try/catch/finally and checkpoints for recovery.

retry · cache · fallback · timeout · checkpoint

Tools and protocols

Create typed tools and use native Git, file, HTTP and JSON operations. Consume MCP/A2A services and serve workflows over those protocols.

tool · git/fs/http · extension · mhl serve

03 / MHL AND FRAMEWORKS

A language dedicated to the flow.

With a framework, you compose a library inside your application. With MHL, the workflow is its own program, with syntax and a runtime for agents, prompts and steps.

Approaches to implementing AI workflows
In practiceWith a framework MHL
What you writeApplication-language code using the library's APIs.A .mh file declaring agents, prompts and execution flow.
What runs itThe application runtime and framework dependencies.The MHL runtime, through the CLI or an MCP/A2A server.
Execution rulesConfigured through each framework's APIs and abstractions.workflow, goto, loop/max, fan-out, parallel and pause/resume expressed in the language.
IntegrationDirect composition with application code and libraries.Commands, tools, HTTP and MCP/A2A extensions at workflow boundaries.
A good fit when…Orchestration needs to be deeply embedded in your application.The workflow needs to be read, versioned and run as a standalone unit.
The difference is where the flow lives.

Frameworks can also offer testing, persistence and observability. MHL's approach is to make orchestration part of the language. Execution rules are explicit; model responses still vary.
