MHL is a small executable language for orchestrating agents, prompts, tools, memory, and external services. Your program owns the flow; AI contributes judgment where it helps.

01 · THE SHAPE OF A PROGRAM

Declare capabilities, then compose a flow.

An MHL file is a readable set of top-level declarations. A pipeline or workflow connects them into ordered steps with explicit inputs, state, limits, and outputs.

CAPABILITIESagent · prompt · toolwhat the workflow can call
→
ORCHESTRATIONpipeline · step · loopwhen and under which limits
→
STATEmemory · memwhat survives the next step
→
INTEGRATIONSMCP · A2A · extensionswhat can live outside MHL
Declarations

Reusable named blocks such as agent, prompt, tool, memory, and extension.

export prompt Review(diff: string) { ... }
Execution

Statements inside a step evaluate values, call capabilities, branch, loop, handle errors, and write state.

var result = Project.test()

03 · INSTALL AND RUN

Go from an empty folder to a running pipeline.

Install the Go runtime, save the example as hello.mh, and run it. The echo agent needs no API key or network connection.

macOS / Linuxcurl -fsSL https://raw.githubusercontent.com/mh-language/mhl-core-runtime/main/install.sh | sh
Windows / PowerShellirm https://raw.githubusercontent.com/mh-language/mhl-core-runtime/main/install.ps1 | iex
agent Echo {
    command: "echo"
    args: ["${prompt}"]
}

prompt Greeting(name: string) {
    "Hello, ${name}. Your first pipeline is running."
}

pipeline Hello {
    input name: string

    step Greet {
        var answer = Echo.run(
            prompt: Greeting(name: name)
        )
        log(answer)
    }
}
runmhl run hello.mh --input name=Ana
checkmhl lint hello.mh mhl test hello.mh
outputHello, Ana. Your first pipeline is running.

04 · EXTEND THE RUNTIME

Add a capability without changing the language.

An external extension is an isolated executable described by a manifest. MHL starts it on demand and communicates through a small JSON-RPC process protocol. The extension owns its capability; the runtime owns orchestration and policy.

PROJECT LAYOUT

my-project/
├── .mhl/
│   └── extensions/
│       └── crm/
│           ├── extension.json
│           └── bin/
│               └── crm
└── workflow.mh
TRUST BOUNDARY

Pin the extension in extensions.lock. Keep credentials out of source and declare only the permissions it needs.

MINIMAL MANIFEST

{
  "id": "crm",
  "api_version": 1,
  "executable": "bin/crm",
  "declarations": [
    { "kind": "crm", "name": "Customer" }
  ],
  "permissions": {
    "network": ["api.example.com"]
  }
}
extension crm Customer {
    endpoint: "https://api.example.com"
}

var customer = Customer.lookup(id: "42")

05 · SERVE YOUR WORKFLOWS

Expose MHL as MCP tools or A2A skills.

The runtime can publish every workflow in a directory. Use MCP over stdio when a client spawns the process, MCP over HTTP for a networked client, or A2A over HTTP for Agent2Agent interoperability.

MCP

Local MCP

Newline-delimited JSON-RPC over a subprocess. One workflow becomes one MCP tool.

mhl serve mcp sample/serve
HTTP

MCP over HTTP

Expose the same workflows through Streamable HTTP for networked clients.

mhl serve mcp --http --addr 127.0.0.1:8711 sample/serve
A2A

A2A skills

Publish workflows as Agent2Agent tasks with an Agent Card and task lifecycle.

mhl serve a2a --addr 127.0.0.1:8710 sample/serve
!
Before exposing a server

Bind deliberately, configure authentication for non-local use, choose a state directory for resumable runs, and review the permissions of every workflow.
