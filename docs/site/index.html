META-HARNESS LANGUAGE · v0.1 ALPHA

Control the loop.
Not the agent.

MHL is a declarative language that turns AI agents, prompts, tools, memory, and operational policies into reproducible pipelines.

Get started → Explore the language

agent Reviewer {
    engine: "ollama/qwen2.5-coder"
    endpoint: "http://localhost:11434"
}

prompt Review(diff: string) {
    "Review the diff and list risks:\n${diff}"
}

pipeline PullRequest {
    step Analyze {
        var diff = git.diff()
        var answer = Reviewer.run(
            prompt: Review(diff: diff)
        )
        log.info(answer)
    }
}

01 · WHY MHL

Agents are probabilistic. Your process does not have to be.

In real engineering workflows, unrestricted agent autonomy makes basic questions hard to answer: what ran, with which data, in what order, under which limits, and how can the process resume after a failure?

01

Invert orchestration

A deterministic harness owns the loop. The model is called only where probabilistic judgment adds value.

02

Make policies explicit

Retry, cache, rate limits, fallback, checkpoints, and iteration limits live beside the flow and enter code review.

03

Preserve replaceability

The pipeline describes intent; CLI agents, local models, and integrations can change without rewriting orchestration.

Core principle

Use conventional software for control, state, and verification. Use AI for interpretation, synthesis, and decisions under uncertainty.

02 · POSITIONING

A harness language, not another framework.

Frameworks are libraries embedded in a host application. MHL is a small, independent executable format designed to describe the workflow's operational contract itself.

DecisionAgent frameworkMHL
Unit of workCode in the framework's host languageDeclarative, executable .mh file
Flow controlCallbacks, graphs, or library conventionsSteps, loops, goto, break, and explicit policies
Replacing an agentOften requires SDK-specific adaptersChange the agent declaration; keep the pipeline
State and recoveryInfrastructure added to the applicationmemory, mem, checkpoints, and --resume
InspectionDistributed across code and configurationFlow and limits are readable in one versioned artifact
Best fitFull applications and deep integrationsEngineering harnesses, local automation, and controlled loops
CHOOSING

MHL complements applications and frameworks. Use it when the flow must be portable, auditable, and controlled by a deterministic layer; use a framework when orchestration must live deeply inside the application.

03 · GETTING STARTED

From zero to your first pipeline.

Install the runtime, save the example as hello.mh, and run it. The agent uses echo, so this tutorial needs neither an API key nor network access.

macOS / Linuxcurl -fsSL https://raw.githubusercontent.com/mh-language/mhl-core-runtime/main/install.sh | sh
Windows / PowerShellirm https://raw.githubusercontent.com/mh-language/mhl-core-runtime/main/install.ps1 | iex
agent Echo {
    command: "echo"
    args: ["${prompt}"]
}

prompt Greeting(name: string) {
    "Hello, ${name}. Your first pipeline is running."
}

pipeline Hello {
    input name: string

    step Greet {
        var answer = Echo.run(
            prompt: Greeting(name: name)
        )
        log.info(answer)
    }
}
runmhl run hello.mh --input name=Ana
outputHello, Ana. Your first pipeline is running.

04 · MENTAL MODEL

Declare capabilities. Compose the flow. Execute with limits.

An MHL file separates reusable building blocks from execution order. This keeps operational decisions visible without mixing them into agent code.

DECLARATIONSagent · promptwho reasons and with which context
→
CAPABILITIEStool · memory · MCPwhat the flow can do and remember
→
ORCHESTRATIONpipeline · step · looporder, limits, and recovery
Declarations

Named top-level blocks. They can be exported and reused by other modules.

export prompt Review(...)
Expressions and statements

They live inside steps and tools: variables, calls, objects, arrays, conditions, loops, and error handling.

var ready = result.exit_code == 0

06 · APPLIED EXAMPLE

An engineering loop with explicit stop criteria.

This example connects an agent, prompt, tool, and persistent state. The runtime executes a test, asks for a fix only when necessary, and stops on success or at the attempt ceiling.

agent Fixer {
    engine: "ollama/qwen2.5-coder"
    endpoint: "http://localhost:11434"
    temperature: 0.1
    retry: { max_attempts: 3, delay: 2s }
    cache: { ttl: 10m }
}

prompt Repair(diff: string, failure: string) {
    """
    Change as little code as possible to fix the failure.

    Current diff:
    ${diff}

    Test failure:
    ${failure}
    """
}

tool Project {
    test() -> cmd.exec(["go", "test", "./..."], timeout: 2m)
    diff() -> git.diff()
}

loop pipeline AutoRepair {
    mem attempts = 0
    mem done = false

    repeat: {
        stop_when: done
        max_iterations: 5
    }

    step Verify {
        var result = Project.test()
        if (result.exit_code == 0) {
            done = true
        } else {
            attempts = attempts + 1
            var patch = Fixer.run(prompt: Repair(
                diff: Project.diff(),
                failure: result.stderr
            ))
            fs.write("candidate.patch", patch)
        }
    }
}
1

Verify with a deterministic command.

2

Call AI only after an objective failure.

3

Bound agent retries and pipeline iterations.

4

Persist progress to inspect and resume the loop.

07 · FOUNDATIONS

The idea behind the language.

MHL materializes the Inverted Orchestration pattern: a deterministic harness keeps control of transitions, state, verification, and limits while specialized agents operate within that boundary.
