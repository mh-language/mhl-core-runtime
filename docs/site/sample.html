A development loop you can inspect.

This sample uses MHL as the deterministic harness around Codex. MHL owns sequencing, state, retry limits, verification, and commits; Codex is called only for planning and code changes.

THE REAL EXECUTION ORDER

One main path, three controlled branches.

A fresh run follows the numbered stages below. A resumed run can skip plan loading and setup when pending state already exists. Failures return through explicit routes instead of giving the agent control of the loop.

  1. 01Startload or restore
  2. 02Planonly if missing
  3. 03Setupconfigure target
  4. 04Bearingscapture context
  5. 05Smokebootstrap gate
  6. 06Pickready feature
  7. 07Implementbounded Codex run
  8. 08Verifydeterministic check
  9. 09Replanafter repeated failure
  10. 10Handoffrecord and commit
BOOTSTRAP FAILURE

Smoke → Bearings → Smoke after Codex repairs only the startup process.

VERIFY FAILURE

Verify → Implement with a focused fix prompt and the latest failure evidence.

THIRD FAILURE

Verify → Replan → Bearings while the global replan budget remains.

BEFORE STAGE 01

Prepare the specifications and the execution boundary.

The sample ships with specifications for a .NET and Postgres task-management API. Replace those documents to drive another project, then run MHL from the workflow directory so every relative path resolves correctly.

01

Install the tools

Make mhl, codex, git, and bash available. Start Docker when the target specifications require local services.

02

Provide the plan

Place the approved plan at specs/active/40-development-plan.json. If it is absent or invalid, keep source material in specs/sources/ for the fallback planner.

03

Review the prompts

Codex can edit files and run commands. Review the active specs and Markdown prompts before granting that authority.

PLAN CONTRACT

Every feature needs an ID, priority, dependency list, description, traceable references, implementation context, and status. Dependencies must point to existing IDs and form an acyclic graph.

LANGUAGE ANATOMY

Each MHL feature has one job.

The workflow keeps orchestration in main.mh, reusable deterministic operations in tools, agent integration in an adapter, and natural-language instructions in external Markdown prompts.

MHL featureUse in this workflowWhy it matters
use {A as alias} from "…"Imports the feature store, configuration, adapters, schemas, and operational tools.Keeps the pipeline short and modules independently testable.
prompt Name(...) from "file.md"Loads setup, plan, implement, fix, replan, and smoke instructions from Markdown.Prompt changes remain reviewable without hiding control flow.
loop pipeline + repeatProcesses features until none remain, with a hard ceiling of 15 iterations.The runtime—not Codex—decides when another cycle starts or stops.

01Start · restore or initialize

CONTROL

The entry stage decides whether this is a continuation or a fresh feature cycle. Existing pending state goes directly to Bearings; otherwise the store and configuration are reset before plan import.

step Start {
    if (store.has_pending_features() == true)
        goto Bearings

    store.reset()
    config.reset()

    if (store.try_import_preview_plan() == false)
        goto Plan
    else
        goto Setup
}

FEATURES USED

  • step creates a named checkpoint boundary.
  • if inspects deterministic persisted state.
  • goto makes resume and fallback routes explicit.

NEXT

A valid published plan goes to Setup. A missing or invalid plan goes to Plan. Restored pending work goes to Bearings.

02Plan · create the fallback plan

AGENT

This stage runs only when the published JSON plan could not be imported. MHL concatenates the source specifications, asks Codex to write the canonical plan, then parses and validates the file before execution can continue.

step Plan {
    var content = store.read_files_in_source_folder(
        "./specs/sources")
    var plan_path =
        "specs/active/40-development-plan.json"

    adapter.execute_without_schema(
        query: PlanPrompt(
            plan_path: plan_path,
            content: content))

    var plan = json.parse(fs.read(plan_path))
    if (store.set_plan(plan) == false) {
        fail("Codex did not produce a valid feature list")
    }
}

FEATURES USED

  • var holds stage-local source and path values.
  • An external prompt receives typed arguments.
  • fs.read and json.parse turn the generated artifact back into data.
  • fail blocks execution when validation rejects the plan.

NEXT

Normal step order continues to Setup. No feature is implemented from an unvalidated plan.

03Setup · establish the project contract

AGENT + SCHEMA

Codex classifies the target as greenfield or brownfield, prepares a safe feature branch, and returns the target directory and verification command. Unlike planning, this call must conform to a JSON schema.

step Setup {
    var schema = schemas.get_setup_schema_path()
    var result = adapter.execute(
        prompt: SetupPrompt(),
        schema_path: schema)

    if (result == null) {
        fail("Setup returned no result")
    }

    var raw = json.parse(result)
    config.setup(raw)
}

FEATURES USED

  • The adapter constrains agent output with schema_path.
  • json.parse converts the response to an object.
  • config.setup persists TARGET_DIR, VERIFY_CMD, and limits.

TARGET CONTRACT

The target must expose idempotent init.sh, real verify-feature.sh, concise progress.txt, and detailed logs/smoke.log.

04Bearings · refresh concise context

TOOL

Before bootstrap, and again after a smoke repair or accepted replan, the workflow captures a compact repository snapshot. It records the target path, the contents of progress.txt, and the ten most recent commits.

mem bearingkey = "current_bearings"

step Bearings {
    session.set(
        bearingkey,
        bearings.snapshot())
}

FEATURES USED

  • mem keeps the key across loop iterations and checkpoints.
  • A reusable tool performs deterministic repository inspection.
  • The session module stores the snapshot and emits trace data.

NEXT

Normal execution continues to Smoke.

05Smoke · prove the project can start

TOOL → AGENT ON FAILURE

The deterministic smoke tool runs <TARGET_DIR>/init.sh and writes the command and detailed result to logs/smoke.log. Codex enters only when that gate fails, with instructions to repair the bootstrap process rather than implement a feature.

step Smoke {
    var result = smoke.execute()
    if (result.success == false) {
        adapter.execute_without_schema(
            query: SmokePrompt(
                log_path: result.logPath))
        goto Bearings
    }
}

FEATURES USED

  • The tool returns structured success and log-path fields.
  • The failure prompt points Codex to concrete evidence.
  • goto Bearings refreshes context, then naturally runs Smoke again.

NEXT

Success falls through to Pick. Failure follows Bearings → Smoke until bootstrap succeeds or execution is externally stopped.

06Pick · select one ready feature

CONTROL

Selection is deterministic: only pending features whose dependencies are complete are eligible, ordered by priority and then ID. Per-feature retry counters are reset exactly when the selection changes.

step Pick {
    if (store.has_pending_features() == false) {
        break
    }

    var next_feature = store.pick_next_feature()
    if (next_feature == null) {
        fail("Pending features are blocked")
    }

    current_feature = next_feature
    feature_steps = 0
    verify_failures = 0
    verify_result = ""
    session.append("current_feature", next_feature)
}

FEATURES USED

  • break ends the loop cleanly when work is complete.
  • fail distinguishes “finished” from “pending but impossible to order.”
  • Assignments update checkpointed mem values.

NEXT

A ready feature continues to Implement. A dependency deadlock stops with a pointer to .mhl/feature_list.json.

07Implement · run one bounded coding task

AGENT

MHL sends Codex only the selected feature, its traceable references, relevant design decisions, the target directory, and—on retries—the latest verification failure. A per-feature guard prevents an endless implement/verify loop.

step Implement {
    feature_steps = feature_steps + 1
    if (feature_steps > config.steps_per_feature()) {
        fail("Feature exceeded its attempt limit")
    }

    var fctx = implement.get_feature_context(
        feature: current_feature)
    var dctx = implement.get_design_context()

    if (verify_failures == 0) {
        adapter.execute_without_schema(
            query: ImplementPrompt(/* scoped context */))
    } else {
        adapter.execute_without_schema(
            query: FixPrompt(
                verify_failure: verify_result,
                /* scoped context */))
    }
}

FEATURES USED

  • mem feature_steps enforces the default six-cycle budget.
  • Separate external prompts distinguish first implementation from targeted repair.
  • The adapter owns Codex CLI execution, JSON event parsing, logging, and errors.

NEXT

A non-null agent result falls through to Verify. Missing output or an exhausted attempt budget fails the run.

08Verify · gate progress with evidence

DETERMINISTIC GATE

The verifier runs verify-feature.sh <feature-id>, falling back to the configured aggregate command when needed. The process exit code—not the agent's opinion—decides whether work passes.

step Verify {
    if (verify.verify_feature(current_feature) == false) {
        verify_failures = verify_failures + 1
        verify_result = "FAIL: verification failed"

        if (verify_failures >= 3 &&
            replans < config.max_replans()) {
            store.record_observation(/* evidence */)
            goto Replan
        }

        goto Implement
    }

    verify_result = "PASS: verified successfully"
    store.mark_done(current_feature.id)
    goto Handoff
}

BRANCH RULES

  • Pass: mark the feature done, then go to Handoff.
  • Failure 1–2: go to Implement with a fix prompt.
  • Failure 3+: go to Replan while replan budget remains.
  • After the replan budget is spent, fixes can continue only until the per-feature attempt limit stops the run.

FEATURES USED

Boolean tool results drive if; checkpointed counters drive escalation; goto encodes every outcome.

09Replan · revise the plan under validation

AGENT + VALIDATOR

Repeated deterministic failures may reveal a bad decomposition or missing dependency. Codex receives accumulated observations and writes a proposal; the feature store validates positive unique IDs, retention of completed features, dependency existence, self-dependencies, cycles, and size limits, then normalizes statuses before applying it.

step Replan {
    replans = replans + 1
    if (replans > config.max_replans()) {
        fail("Reached the replan limit")
    }

    store.clear_revision_proposal()
    adapter.execute_without_schema(
        query: ReplanPrompt(
            observations: store.get_observations_text(),
            current_plan: store.current_plan_json(),
            proposal_path: store.revision_proposal_path()))

    var outcome = store.apply_revision_file()
    if (outcome.success == false) goto Replan

    verify_failures = 0
    feature_steps = 0
    goto Bearings
}

FEATURES USED

  • The model proposes; a deterministic tool accepts or rejects.
  • A rejected proposal loops inside Replan and consumes the replan budget.
  • An accepted proposal clears feature-local failures but preserves the global replan count.

NEXT

Accepted plans return to Bearings, then pass through Smoke and feature selection again so execution uses fresh context and the revised dependency graph.

10Handoff · record and commit verified work

TOOL

Handoff runs only after Verify marks a feature complete. The tool appends a concise progress entry, stages the target repository, and creates a feature-specific commit when there are changes. The result is written to the session trace.

step Handoff {
    var result = handoff.commit_feature(
        current_feature,
        verify_result)

    session.append("handoff", {
        feature_id: current_feature.id,
        verify_result: verify_result,
        result: result
    })
}

COMMIT FORMAT

Feature #<id> - <title>: implementation completed [<result>]

WHAT HAPPENS NEXT

The loop reevaluates stop_when. If no pending features remain, the pipeline ends. Otherwise the next iteration starts at Start, restores state, refreshes Bearings and Smoke, then selects the next dependency-ready feature.

BEST EFFORT

progress.txt can still be updated when no commit is created. The tool skips a commit when the target is not a Git repository, there are no staged changes, or Git reports an error; the result remains visible in the trace.

STATE AND SAFETY

Everything needed to resume or audit the run is explicit.

MHL writes runtime state under .mhl/ inside the workflow directory. Checkpoints retain each completed stage for seven days; supporting files expose configuration, feature status, evidence, proposals, and raw agent events.

.mhl/run_config.json

Target directory, verification command, and execution limits.

.mhl/feature_list.json

The imported or revised feature graph and current status.

.mhl/plan_observations.json

Verification evidence accumulated for replanning.

.mhl/plan_revision.json

The temporary revision proposal awaiting validation.

.mhl/session_trace.jsonl

Selected features, refreshed bearings, and handoff outcomes.

.mhl/logs/codex.log

Raw Codex CLI JSON events for diagnosis and audit.
