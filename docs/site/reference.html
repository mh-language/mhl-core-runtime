META-HARNESS LANGUAGE · REFERENCE · v0.2

What the runtime actually does.

This is a feature-by-feature reference for every .mh declaration and language construct, sourced directly from src/mhl-runtime — not from the design docs, which describe surface that sometimes outruns the implementation. Every claim here cites the exact file and line it comes from. Where the runtime falls short of the docs, or a field parses but does nothing, that's called out explicitly as a gap rather than glossed over.

Implemented works as described, exercised by tests Partial real, but with a named limitation Docs-only parses, but nothing executes it

01Program structure

Partial

import, use, and the export modifier are how one .mh file makes declarations available to another. Only one of the two actually grants access.

Example

// memory.mh
export memory Store {
    type: "kv"
    store: "memory"
}

// tool.mh
use {Store as store} from "memory.mh"
export tool Counter {
    pending() -> store.get("n", 0)
}

// pipeline.mh
use {Counter as counter} from "tool.mh"
pipeline P {
    step S {
        log(counter.pending())
    }
}

Variations

FormEffectGrants access?
import "path" as aliasParses and validates the target file onlyNo — alias is never registered
use { Name } from "path"Merges the named exported declaration into this fileYes, under its own name
use { Name as x } from "path"Same, plus registers x as an alias for NameYes, under x
export (prefix on any declaration)Marks the declaration visible to useGate, not itself an import

Runtime behavior

  • import resolution (imports.go:74-77) calls loadModule and discards the result — the parsed declarations are never merged into the program, and Import.Alias is never recorded anywhere except an error string. There is no code path that resolves alias.Name.
  • use resolves each path relative to the importing file's own directory, not the process cwd (imports.go:20-23), recursively resolving the target's own use/import first — so a re-exported name works transitively.
  • Every requested name is looked up via findExport, which only matches declarations with Export == true (imports.go:246-269) — a hard runtime gate, not a lint-only hint.
  • use merges the entire mergeable declaration set from the target module, not just the requested names (imports.go:118-124). test blocks are explicitly excluded from merging (imports.go:181-200), so use-ing a file never drags its test suite along.
  • A diamond dependency (two files both use-ing a common third file) is deduplicated by absolute path, not an error (imports.go:91-102, 207-214).
  • No cycle detection exists. A module is marked resolved before recursing into its own imports; a cycle just silently stops recursing rather than erroring — a name only reachable via the unfinished side of the cycle simply isn't found.

Errors

use/import target unreadable/unparseableuse {%s} from %q: %w / import %q as %s: %wimports.go:96,76

Known gap
  • docs/language-design.md shows import "..." as qa implying qualified access (qa.SomeAgent.run(...)) — that access pattern is not implemented. Real cross-file access always goes through use { Name [as alias] } from "path".

02agent

Partial

Declares a callable AI backend — a local CLI subprocess or an Ollama HTTP endpoint — with resiliency policy attached. Core dispatch, retry, cache, rate-limiting, and fallback are all real; several documented fields are silently inert.

Example

export agent GeminiAPI {
    command: "sh"
    args: ["-c", "curl -s ... \"${prompt}\"", "gemini-api", "${prompt}"]

    retry: {
        max_attempts: 3
        delay: 2s
        retry_on: [500, 503, "rate_limit", "timeout"]
    }

    cache: { ttl: 1m }
    fallback: [ClaudeCLI]
}

agent LocalModel {
    engine: "ollama/qwen2.5-coder"
    endpoint: "http://localhost:11434"
    temperature: 0.2
}

var answer = GeminiAPI.run(prompt: "Summarize this diff.", schema: schema_text)

fallbackagent.go:568-596array of agent names/inline agents, tried in order on failure

Runtime behavior

  • Agent has no fixed grammar (ast/agent.go) — its body is a generic []*Property bag, identical for every field name. Whether anything happens depends entirely on whether agent.go reads that key.
  • Dispatch order in runAgentAttempt (agent.go:115-232): read engine → branch → read cache, compute traffic.RequestKey, check cache → read retry/rate_limit → acquire limiter → run subprocess/HTTP call → append to log if set → trim + require non-empty response → retry via retrier.Execute → store to cache on success.
  • .run(prompt:, schema:) dispatch happens in evalPostfix before generic identifier resolution (eval.go:389-395). prompt: must resolve to a string or a recognized prompt-template call; schema: accepts any string expression.
  • schema:'s effect depends on the engine: for cli/* it's spliced wherever "${schema}" appears in args (error if declared without a value supplied, silent no-op if args never references it, agent.go:289-301); for ollama/* it's sent as the real format field on /api/generate (adapters/ollama.go:64-65). No response is ever validated against the schema — it only shapes the outgoing request.
  • Cache key = SHA-256 of {engine, prompt, parameters} (traffic/cache.go:34-42) — deliberately excludes command/args/endpoint/temperature, so two agents sharing engine+prompt+schema but different commands could collide (an undocumented latent edge case, not a flagged gap). Default TTL is 24h when unset (agent.go:466); cache.storage: "disk" additionally persists one JSON file per key under .mhl-cache/.
  • On failure, fallback legs run in declaration order; the response is the first success or the last failure (agent.go:58-76).

03prompt

Implemented

A named, parameterized text template — inline or loaded from an external Markdown file — composable into other prompts and passed to agent.run(prompt: ...).

Example

export prompt SecurityExpertRole() {
    "Você é um especialista em segurança de software."
}

export prompt SystemPrompt(role: prompt, task: string) {
    """
    ${role}

    ${task}
    """
}

prompt SecurityAuditPrompt(file_path: string, code: string) from "./security-audit.prompt.md"

var response = Echo.run(prompt: SystemPrompt(
    role: SecurityExpertRole(),
    task: "Revise o pull request #42."
))

Variations

inline body

prompt Name(params) { "..." } or a """...""" block — mutually exclusive with from.

external file

prompt Name(params) from "file.md" — the file's trimmed contents become the body at import-resolution time, indistinguishable from an inline body thereafter.

two interpolation engines

Ordinary strings anywhere interpolate a full expression inside ${...} via interpolate.go — variables, calls, anything. A prompt template body interpolates only bare identifiers via a fixed regex in prompt.Render, with \${name} as a literal-text escape (needed because text pulled from a Markdown file often has incidental ${...}).

Runtime behavior

  • resolvePromptArgument (prompt_ops.go:23-46): a bare Name(...) call is treated as a reference to a declared prompt and rendered via renderPromptCallDynamic; anything else is evaluated as an ordinary expression and must produce a string.
  • Every nested prompt-call argument must be named and must evaluate to a string (prompt_ops.go:66,74) — nested prompts compose naturally (role: SecurityExpertRole() inside another prompt call).
  • prompt.Render is fail-closed: a declared parameter with no supplied value, a supplied argument that isn't a declared parameter, or a template referencing an undeclared ${name} are all hard errors, not silently ignored.

04skill

Docs-only

Declares a named, scoped capability — description, allowed tools/MCP servers, input/output schema, system instructions. Parses completely and is listed by mhl skills list, but nothing in the runtime ever invokes a skill or scopes an agent to it.

Example

export skill CodeAuditorSkill {
    description: "Analisa código."
    tools: [execution.read_file, execution.git_diff]
    mcp_servers: [PostgresDB]

    input {
        target_file: string
        strict_mode: boolean
    }

    output {
        vulnerabilities_found: int
        report_markdown: string
    }

    system_instructions: """
    Você é um auditor de segurança sênior.
    """
}

Fields

FieldParsed?Executed at runtime?
descriptionyesprinted by mhl skills list only
tools, mcp_serversyesprinted by the CLI listing; otherwise unreachable
system_instructionsyesonly merged inside code that nothing calls
input { }, output { }yes, into a schema structnever read anywhere, not even by the CLI listing

Runtime behavior

  • A skill is treated by internal/engine/interpreter only as one more exportable declaration kind for use resolution — nothing else (imports.go:183-184,254).
  • The real logic lives in internal/features/skills: PrepareAgentPayloadForSkill (resolver.go:64-99) computes a genuinely sandboxed payload — system instructions tagged [ACTIVE SKILL: name], tool/MCP lists scoped to the skill's own lists — but is called only from that package's own unit tests, never from internal/engine/interpreter or internal/cli.
  • mhl skills list [dir] parses every .mh file independently (no import resolution) and prints description/tools/mcp_servers per skill — export has no effect on this listing, unlike use.
!
Known gap
  • There is no .mh syntax anywhere for actually invoking a skill from a pipeline. Declaring one documents intent and shows up in mhl skills list; it never restricts what an agent can do at run time.

05memory

Implemented

A named state store, chosen per-declaration by type. Four backends exist, each with a different persistence model and method set.

Example

export memory SessionJsonMem {
    type: "json"
    path: ".mhl/session_mem.json"
}

export memory AuditLogMem {
    type: "append_log"
    path: ".mhl/logs/audit.log"
}

SessionJsonMem.set("key1", "value1")
SessionJsonMem.set({"nested": {"key1": "value1"}})
are_equal(SessionJsonMem.get("nested").key1, "value1")
SessionJsonMem.remove("nested::key1")

AuditLogMem.append("First log entry")

Backends

typePersistenceMethods
kvin-memory only (store: "memory" required) — discarded at process exitget, set
jsonone JSON object file at path, rewritten whole on every writeget, set, remove (all support "::"-delimited nested paths)
append_logplain-text file at path, append-onlyappend(text) only — no read-back method
jsonlJSON-lines file, each entry auto-wrapped with a ts timestampappend(value) only

Runtime behavior

  • Dispatch is executeMemoryOp (memory_ops.go:53-185): read type, evaluate call args positionally only — memory calls accept no named arguments — then switch on type and method.
  • json is the most mature backend: lazily loaded and cached per path, so multiple memory declarations pointing at the same path share one cache entry (json.go:19-27). A missing file starts as an empty object (auto-created on first write, not on load); a malformed existing file is the only load-time error.
  • Path resolution asymmetry: path resolves relative to the process's current working directory, not the declaring .mh file's directory — unlike use/import/prompt ... from, which all resolve relative to the declaring file.
  • Locking is an in-process sync.Mutex only. There is no cross-process file locking, and json's writes are a direct os.WriteFile, not write-temp-then-rename — a crash mid-write can leave a partially-written file.

  • A vector backend is mentioned only in an AST doc comment (program.go:88-92) — declaring type: "vector" hits the generic "not supported yet" default. No TTL exists for any memory backend (that's an agent-level cache concept, unrelated).

06tool

Implemented

A namespace of methods — each either a single expression or a full statement block — that wraps native ops or other calls behind a named, reusable interface.

Example

tool T {
    obj_body() -> {a: 1, b: 2}
    empty_body() -> {}
    block_body(items) -> {
        var count = 0
        while (count < items.size()) {
            count = count + 1
        }
        return count
    }
    pending() -> self.block_body(items: [])
}

Variations

expression body

name(params) -> expr — the method's value is the expression's value directly.

block body

name(params) -> { statements } — a real statement block with var/if/while/return. A block that looks like a single object literal (-> {a: 1}) is still parsed as an expression body, not a block — Body is tried first, and participle only falls back to Block when the content inside { } can't parse as an expression.

self

Inside a tool method, self.other_method(...) calls a sibling method on the same tool. self is only valid inside a tool method body — everywhere else (a pipeline step, a describe, a stop_when) it errors.

Runtime behavior

  • Parameters bind purely positionally, by count — Param's optional : Type annotation is accepted but never checked at call time (tool.go:37-61).
  • Each call gets a fresh Env{} — a real function-call boundary. The method body never sees the caller's step-local variables.
  • Dispatch: evalPostfix checks reserved cases (native namespaces, agent .run, prompt calls, self.*) first, then falls to a generic tool/memory lookup (eval.go:406-427). An expression body evaluates directly; a block body runs through execBlock, and a return inside it supplies the result (falling off the end without one yields nil).

Errors

ConditionMessageLocation
method doesn't existtool %q has no method %qtool.go:46
wrong argument counttool %q: %s requires %d argument(s), got %dtool.go:53
self used outside a tool methodself is only valid inside a tool methodeval.go:397-405

Known gap
  • No recursion or call-depth guard exists for tool-method self-calls (the threaded depth parameter is only used for literal-nesting limits). Deep or infinite recursion runs until the Go call stack overflows — an uncontrolled crash, unlike runtime.Runner's explicit 10,000-visit cap for goto cycles.

07mcp_server

Docs-only

Declares a Model Context Protocol server — stdio or HTTP transport, credentials injected via env(...). The registry and JSON-RPC client are real and independently tested, but nothing in the execution path ever constructs one.

Example

mcp_server PostgresDB {
    transport: "stdio"
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-postgres", env("DATABASE_URL")]
}

mcp_server GitHubServer {
    transport: "http"
    url: "https://mcp.github.com/v1"
    headers: {
        "Authorization": "Bearer " + env("GITHUB_TOKEN")
    }
}

Variations

transport: "stdio"

Spawns command/args, writes one JSON-RPC request line to stdin, reads the first valid JSON line from stdout. Stateless per call — no session or handshake persisted.

transport: "http"

POSTs the JSON-RPC request with headers, unwrapping optional SSE data: framing from the response.

Runtime behavior

  • mcp.BuildRegistry(prog) walks every mcp_server declaration into a ServerConfig; env("KEY") and "prefix" + env("KEY") concatenation are recognized and resolved via the shared credential resolver, with a fail-closed variant that pre-validates every reference resolves before returning.
  • Client.CallTool dispatches on transport to a stdio or HTTP implementation. Tool discovery (tools/list) is not implemented anywhere — the client only exposes calling an already-known request; nothing builds a catalog of a server's available tools.

Known gap — confirmed, total wiring gap
  • Grepping the whole tree for uses of the registry/client outside their own package turns up only their own tests. Nothing in internal/engine/interpreter (agent.go, tool.go, eval.go), internal/engine/runtime, or internal/cli ever imports internal/features/mcp. Declaring an mcp_server today does nothing beyond making it visible to use/export bookkeeping and mhl skills list's echo of a skill's declared mcp_servers: list.

08pipeline / loop pipeline

Implemented

An ordered sequence of steps with optional per-step checkpointing and resume, redirectable with goto. Prefixing with loop repeats the whole pipeline under a repeat policy.

Example

pipeline AutoFix {
    input issue_id: string

    checkpoint: {
        enabled: true
        strategy: "per_step"
        storage: "file"
        ttl: 7d
    }

    step Verify {
        var result = project.test()
        if (result.exit_code != 0) goto Repair
    }

    step Repair {
        log.warn("corrigir e tentar novamente")
    }
}

memory Counter { type: "kv" store: "memory" }

loop pipeline Increment {
    repeat: {
        stop_when: Counter.get("n", 0) >= 3
        max_iterations: 10
    }
    step Bump {
        Counter.set("n", Counter.get("n", 0) + 1)
    }
}

Fields

BlockFieldsNotes
checkpointenabled, strategy, storage, ttlonly strategy: "per_step" and storage: "file" are ever actually branched on — see gap
repeat (loop pipeline only)stop_when, max_iterationseither or both may be absent; a loop with neither runs forever unless a step breaks

Runtime behavior

  • One grammar covers both plain and loop pipelines — Loop is just an optional leading token. checkpoint/repeat aren't dedicated AST nodes, just ordinary properties whose value is a bare object literal, read generically in internal/engine/runtime/pipeline.go.
  • State lives at <root>/.mhl/state/<PipelineName>.json, written atomically (temp file + rename). String variable values are redacted before persisting; non-strings pass through unredacted.
  • --resume: if the prior run finished (NextStep == ""), returns immediately; otherwise resumes at the persisted next step with restored variables, and init is skipped entirely on a resumed run.
  • goto target must be a declared step (forward or backward) — validated at the runtime layer, not the interpreter. A goto cycle with no escaping break is capped at 10,000 step-visits.
  • stop_when runs in a brand-new, empty environment — it has no access to any pipeline or step var, only to memory stores. State a loop condition needs to observe across iterations must go through memory, exactly like a step would use it.
  • Loop terminal reasons are exactly one of three strings: "max_iterations" (checked at the top of each iteration), "break" (a step's explicit break, checked before stop_when for that iteration — break always wins), or "stop_when" (checked only after a full iteration completes). A genuine step error is not a terminal reason — it propagates straight out, aborting the whole run.

Errors

ConditionMessageLocation
goto to an undeclared stepruntime: goto target %q is not a step of pipeline %qrunner.go:147-148
goto cycle exceeds visit capruntime: step %q revisited more than 10000 times (a goto cycle with no break?)runner.go:53,118-121
!
Known gaps
  • checkpoint.strategy — the only value ever branched on is "per_step"; any other value (or none) means no per-step checkpoint is ever saved.
  • checkpoint.storage — accepted and stored on the config, but nothing branches on it. File-based JSON under .mhl/state is hardwired regardless of what (or whether) storage: was declared.
  • Resuming into a step no longer present in an edited pipeline isn't validated up front — it only fails once that step is actually reached during execution.

09test / describe

Implemented

A test block groups named describe cases; assertions are ordinary calls recognized by name, so they can appear nested inside if/while/for-in like any other statement.

Example

test test_conditional_statements {
    describe conditional_expression {
        var result = if (true) "This is true" else "This is false"
        are_equal(result, "This is true")
    }
    describe classical_if_statement {
        var valueA = 0
        var valueB = 1
        var result = if (valueA > valueB) "A" else "B"
        are_equal(result, "B")
    }
}

Variations

Assertion set: are_equal, are_not_equal/not_equal, is_true, is_false, is_null, not_null, greater_than, less_than, greater_than_or_equal, less_than_or_equal, includes, and incomplete(...) — which records a skip and never evaluates its argument for pass/fail.

Runtime behavior

  • Each describe runs against a fresh, empty environment — nothing declared in one is visible to another. There is no shared setup/teardown between describes, and nested describe blocks aren't supported by the grammar (only one level exists).
  • A wrong assertion argument count/type is a genuine Go error that aborts the whole test run — only a value-level mismatch is recorded as a normal failure and execution continues.
  • No source text or line number is captured for a failing assertion — the reported call is reconstructed from the evaluated name and arguments, not the original source span.

10Expressions

Implemented

Operators, member/index/slice access, closures, and a fixed set of built-in value methods — no user-defined functions outside tool methods and closures.

Example

var numbers = [0, 10, 20, 30, 40, 50, 60]
var slice = numbers[^3..]              // [40, 50, 60] — ^ means "from the end"
var even = numbers.filter((n) -> n % 2 == 0)
var found = even.find((n) -> n > 40)
var sorted = even.sort_by((n) -> -n)
var ready = retries < 3 && numbers.size() > 0
var result = if (ready) "continue" else "stop"
log.info("active:", "${sorted}")

Built-in value methods (complete list)

Runtime behavior

  • Slicing (numbers[1..4]) always copies into a new array; out-of-range bounds clamp rather than error. A ^-prefixed bound counts from the end (size - value).
  • A closure (x) -> expr captures a shallow copy of the enclosing environment at creation time — by value, not by reference. Reassigning an outer variable after creating the closure does not change what the closure sees.
  • if (cond) a else b as an expression requires both branches and returns a value; the statement form (no assignment) makes else optional and runs for side effects only.
  • env("KEY") returns os.Getenv directly — a missing variable returns "", with no way to distinguish "unset" from "empty".
  • fail(...) returns a plain error, not a control-flow signal like break/return/goto — a try { fail(...) } catch (e) { } catches it exactly like any other error. It's the mechanism for marking an mhl run genuinely failed for the process exit code.
!
Known boundary (not a bug)
  • The array-method list above is complete — there is no map, reduce, join, reverse, first, or last. An unrecognized method errors "%s value has no method %q" rather than silently returning nil.

11Statements

Implemented

Imperative statements available in a step, a tool method block, a describe, or a closure block body: var, assignment, if/while/for-in, try/catch/finally, return, break, goto.

Example

tool T {
    f() -> {
        try {
            return "from-try"
        } catch (e) {
            return "from-catch"        // never runs — a control signal skips catch
        } finally {
            log("finally-ran")         // always runs
        }
    }
}

pipeline GuardedRetry {
    step Implement {
        var attempts = 4
        if (attempts > 3) break "too many attempts"
    }
    step Handoff {
        var done = true
    }
}

Runtime behavior — try/catch/finally, precisely

  • Body runs. If it errors with a genuine error (not a control signal), catch (e) binds e to the error's message and Catch runs, overwriting the result.
  • If Body's error was a control signal (return/break/goto), step 1 is skipped entirely — Catch never runs — the control signal keeps propagating.
  • Regardless of the above, if Finally is present it always runs; if Finally itself errors, that error unconditionally overrides the result — even a pending return or break from the try body is discarded in favor of the finally error.
  • break/goto inside Body/Catch behave identically to return in this trace — all three are treated as one uniform "control signal" category.

Runtime behavior — loops, goto, break

  • while and for-in are both capped at 10,000 iterations — exceeding it is a hard error, not a silent stop.
  • break has no special "exit the nearest loop" meaning — it always exits the enclosing pipeline step (or loop-pipeline iteration), with an optional reason expression. A break outside any loop is not an error; there's just no loop left to also stop.
  • A bare return in a plain pipeline step is legal — it exits the step early, and since a step produces no value in this runtime, any returned value is simply discarded.
  • goto's target step is validated only at the runtime layer (not inside the interpreter), so a typo'd target is caught at execution time, not parse time.
!
No open gaps
  • This area is fully covered by targeted unit tests, including the subtle finally-overrides-pending-control-signal case above.

12Native ops

Implemented

Exactly six reserved namespaces callable from any expression position: cmd, git, fs, http, json, log. Nothing else is reserved, and there is no mechanism to add a seventh.

Example

}

var diff = git.diff()
var response = http.post("https://api.example.com/hook", body: {"ok": true})
var parsed = json.parse(fs.read("config.json"))
log.warn("attempt", 2, "of", 3)

Runtime behavior

  • cmd.exec/cmd.exec_all run each command in its own process group; a timeout kills the whole group (not just the top process) and raises a genuine catchable error — a timeout is never reported through exit_code.
  • All git.* ops shell out to the literal git binary with no path configurability.
  • http.post is the only HTTP verb implemented — there is no http.get/put/delete.

13CLI

Implemented

Five subcommands, dispatched from a single entry point; every non-nil error from cli.Run becomes exit code 1 with an "mhl: <err>" line on stderr.

Commands

mhl run <file.mh> [--input k=v ...] [--resume]run pipeline
mhl test <file.mh|dir>run test blocks
mhl lint [dir]validate source and imports
mhl skills list [dir]list declared skills
mhl lsplanguage server over stdio

Runtime behavior

  • --input is repeatable and parsed as key=value via a single strings.Cut on the first =; a later duplicate key silently overwrites an earlier one.
  • lint's target directory is the only positional argument across all five subcommands that defaults (to ".") rather than being required.
  • skills list exits 0 with "No skills declared..." when none are found — unlike test, where zero test blocks anywhere is a hard error.
  • mhl lsp hands off entirely to internal/lsp, treating its out writer as a raw JSON-RPC protocol stream — the one subcommand where out isn't user-facing text.

Exit codes

  • run exits 1 on any parse/exec/import error — there's no distinct code for a failed pipeline step versus any other kind of error.
  • test exits 1 both when any assertion fails and when zero test blocks are found; an incomplete(...) assertion never counts as a failure.
  • lint exits 1 whenever any findings exist, 0 otherwise.

Cross-cutting: LSP completion drift

The project's own CLAUDE.md warns that internal/lsp's completion tables duplicate the interpreter's knowledge by hand, with no shared source of truth. Two concrete instances of that drift, confirmed while researching this page:

  • internal/lsp/symbols.go's per-type memory method table omits json's remove method, even though memory_ops.go implements it.
  • internal/lsp contains zero references to any native-op name (cmd.exec, fs.read, git.diff, ...) — editor completion offers nothing for any of the six reserved namespaces.
