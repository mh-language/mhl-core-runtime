MHL · SERVING WORKFLOWS · v1.2.0-alpha

Turn a folder of workflows into a server.

mhl serve exposes every pipeline/workflow declared under a directory to another agent — as Model Context Protocol tools or Agent2Agent skills — without writing any server code. This page is the server side; calling out to someone else's MCP or A2A server is extension mcp / extension a2a in the reference.

mcp stdiospawned subprocess mcp --httpnetworked client mhl_run_*long runs, step by step a2aAgent2Agent skills

01The serve model

Executable

Every transport publishes one tool / skill per declaration found under the directory (default .). Each derives its input contract from the workflow's input name: Type declarations — every input required, unknown inputs rejected — and its description from an optional description: "..." body property. A call runs the workflow through the same engine as mhl run and returns its final variable state.

TransportCommandShape
stdiomhl serve mcp <dir>newline-delimited JSON-RPC 2.0 on stdin/stdout — the form an MCP client uses when it spawns the server
Streamable HTTPmhl serve mcp --http <dir>one JSON-RPC message per POST /mcp, JSON responses only (no SSE) — the form a networked MCP client uses
A2Amhl serve a2a <dir>JSON-RPC 2.0 over HTTP with an Agent Card at /.well-known/agent-card.json
ISOLATION

A synchronous tools/call runs in its own throwaway state directory — no checkpoint or context.vars carry-over between calls. The async path (mhl_run_* tools, below) keeps state so a run can be resumed.

02Try it with the sample

Executable

The repository's sample/serve/ directory holds four self-contained workflows (no real LLM needed) used by every example on this page.

git clone https://github.com/mh-language/mhl-core-runtime
cd mhl-core-runtime

mhl serve mcp sample/serve          # stdio
mhl serve mcp --http sample/serve   # http://127.0.0.1:8711/mcp
mhl serve a2a sample/serve          # http://127.0.0.1:8710/
WorkflowSignatureShows
SummarizeSummarize(topic, max_words)a before-free agent step (uses echo, so no real LLM)
TriageTriage(title, body)pure string logic, no agent
ReportReport(topic)four ~1s steps — watch mhl_run_status advance step by step
ApprovalApproval(request, approved)a pause() gate — the paused / mhl_run_resume loop

03MCP over stdio

Executable

mhl serve mcp <dir> speaks newline-delimited JSON-RPC 2.0 on stdin/stdout — the form an MCP client uses when it spawns the server as a subprocess. One tool per declaration; tools/call returns the final variable state (isError: true on a run failure). Diagnostics go to stderr; stdout is the raw protocol stream.

Initialize, list tools, and call a workflow

printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/list"}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"Triage","arguments":{"title":"api outage","body":"everything is down"}}}' \
| mhl serve mcp sample/serve
DUAL-ERA

Both protocol modes work on one connection: the initialize / notifications/initialized handshake (revisions 2025-11-25 / 2025-06-18 / 2025-03-26), and the stateless 2026-07-28 form where every tools/* request carries params._meta with io.modelcontextprotocol/protocolVersion + io.modelcontextprotocol/clientCapabilities and server/discover replaces initialize. A stateless request missing that _meta is rejected with -32602.

04MCP over Streamable HTTP

Executable

mhl serve mcp --http [--addr host:port] [--token t] [--state-dir path] <dir> serves the same tools over the transport a networked client uses: one JSON-RPC message per POST /mcp, JSON responses only. Default bind 127.0.0.1:8711.

Flag / envDefaultEffect
--addr127.0.0.1:8711bind address; a warning is printed if it is non-loopback and no token is set
--token · MHL_SERVE_TOKEN(unset)when set, every request must carry Authorization: Bearer <token> — the gateway↔server shared secret
--principal-header · MHL_SERVE_PRINCIPAL_HEADER(unset)header an authenticated upstream sets the caller identity in; run ownership keys on it (needs --token). Also reaches a workflow as read-only context.principal
--state-dir · MHL_SERVE_STATE_DIRper-process temp dirwhere async run/* state is kept — a real path makes runs survive a restart
--drain-timeout · MHL_SERVE_DRAIN_TIMEOUT0on SIGTERM, how long in-flight async runs get to finish before they are cancelled
--max-concurrent-runs · MHL_SERVE_MAX_CONCURRENT_RUNS0 (unlimited)ceiling on executing runs; an extra mhl_run_start reports state: "queued" with a queuePosition

Operational endpoints, unauthenticated: GET /healthz (liveness), GET /readyz (503 while draining), GET /metrics (Prometheus text). POST /mcp/<method> (e.g. /mcp/run/resume) mirrors POST /mcp so a policy engine can gate one method. A single extension store <Name> { dir: ... } declaration in the workflow directory routes all durable state (sessions + run/* checkpoints) through that extension instead of .mhl/state — see extensions.

Guards: the Origin header, when present, must be loopback (DNS-rebinding). GET /mcp is 405 (no server-to-client stream). DELETE /mcp with an Mcp-Session-Id ends that session (204, or 404 if unknown).

Standard lifecycle — initialize returns an Mcp-Session-Id header the client echoes on every later request

mhl serve mcp --http --addr 127.0.0.1:8711 sample/serve &

sid=$(curl -sD - -o /dev/null -X POST localhost:8711/mcp -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{}}}' \
  | awk 'tolower($1)=="mcp-session-id:"{print $2}' | tr -d '\r')

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"Triage","arguments":{"title":"api outage","body":"everything is down"}}}'

curl -s -X DELETE localhost:8711/mcp -H "Mcp-Session-Id: $sid"   # 204 — end the session

Stateless — no session, every request carries params._meta

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,
  "method":"tools/call","params":{"name":"Triage","arguments":{"title":"x","body":"y"},
    "_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28",
             "io.modelcontextprotocol/clientCapabilities":{}}}}'
# an unknown Mcp-Session-Id is 404; missing _meta with no session is -32602

05Long runs: mhl_run_start, mhl_run_status, mhl_run_cancel

Executable

A plain tools/call blocks until the workflow finishes. For a long one, call mhl_run_start instead — same workflow, but it returns a runId right away; then poll mhl_run_status for the current step, the steps reached so far, and the final vars. mhl_run_cancel stops a run and mhl_run_list enumerates yours. These are ordinary tools, so any MCP client drives them — each is a tools/call like any other, and its status object comes back as structuredContent.

Start, poll, and cancel — all through tools/call

rid=$(curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"mhl_run_start",
       "arguments":{"workflow":"Report","arguments":{"topic":"caching"}}}}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["result"]["structuredContent"]["runId"])')

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":5,\"method\":\"tools/call\",\"params\":{\"name\":\"mhl_run_status\",\"arguments\":{\"runId\":\"$rid\"}}}"
# structuredContent -> {"state":"working","step":"Gather","stepIndex":1,"stepTotal":4,"reached":["Gather"], ...}
# structuredContent -> {"state":"working","step":"Summarize","stepIndex":3,"stepTotal":4,"reached":["Gather","Analyze","Summarize"], ...}
# structuredContent -> {"state":"completed","reached":["Gather","Analyze","Summarize","Publish"],"vars":{ ... }}

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":6,\"method\":\"tools/call\",\"params\":{\"name\":\"mhl_run_cancel\",\"arguments\":{\"runId\":\"$rid\"}}}"
# structuredContent -> {"state":"canceled", ...}

The status object — returned as structuredContent, and mirrored in the result's text block

FieldWhenMeaning
statealwaysworking · completed · failed · canceled · paused
step · stepIndex · stepTotalonce a step has startedthe step the run is on, its 1-based position, and the declared step count
reachedalwaysordered steps that started; on completion it becomes the authoritative executed list
varscompletedthe run's final variable state
error · resumablefailed / canceledthe failure message, and whether mhl_run_resume can continue it
reasonpausedthe pause(...) value — a human-in-the-loop hand-off; vars and resumable are also set
OWNERSHIP

Each run is owned by the session (Mcp-Session-Id) that started it. mhl_run_status, mhl_run_resume, mhl_run_cancel and mhl_run_list only act for that caller — any other sees unknown runId (the same answer as a genuinely unknown id, so it is not an existence oracle). Stateless callers have no session and share one anonymous owner, so stateless mode has no per-caller isolation. Terminal runs stay pollable for an hour; a server shutdown cancels any still running.

RAW METHODS

Each mhl_run_* tool is a thin bridge over a same-named custom JSON-RPC method — run/start, run/status, run/resume, run/cancel, run/list, run/logs — that takes {name, arguments} / {runId} directly and returns the bare status object with no tools/call envelope. Reach for those only when a policy gateway must match one method by name (POST /mcp/run/resume); from an ordinary MCP client, use the tools. Every per-workflow tools/list entry carries _meta.mhl.run.tool: "mhl_run_start" as a hint that it can also be driven async.

06Human-in-the-loop: pause() + mhl_run_resume

Executable

A gate step calls pause("...") to hand off to a human: the run parks in state: "paused" — not failed, not completed — resumable, with the reason and the vars-so-far in its status, and its state kept (unlike a completed run). mhl_run_resume with {runId, arguments} re-enters that same step, merging arguments over the originals — that is where the approval decision goes. pause() writes its own checkpoint, so no checkpoint {} block is required; a step that calls fail("...") instead lands in state: "failed" and needs checkpoint { strategy: "per_step" } to be resumable.

Approval workflow

workflow Approval {
    description: "Prepare, wait for human approval, then finish."

    input request: string
    input approved: string   // "no" on mhl_run_start, "yes" on mhl_run_resume

    var summary = ""

    step Prepare { summary = "ready to act on: " + request }

    step Gate {
        if (approved != "yes") {
            pause("awaiting approval for: " + request)
        }
    }

    step Act { summary = "acted on: " + request }
}

Start, inspect, and resume — all through tools/call

rid=$(curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"mhl_run_start",
       "arguments":{"workflow":"Approval","arguments":{"request":"ship it","approved":"no"}}}}' \
  | python3 -c 'import sys,json;print(json.load(sys.stdin)["result"]["structuredContent"]["runId"])')

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":8,\"method\":\"tools/call\",\"params\":{\"name\":\"mhl_run_status\",\"arguments\":{\"runId\":\"$rid\"}}}"
# structuredContent -> {"state":"paused","step":"Gate","reached":["Prepare","Gate"],"resumable":true,"reason":"awaiting approval for: ship it"}

# a human approves
curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d "{\"jsonrpc\":\"2.0\",\"id\":9,\"method\":\"tools/call\",\"params\":{\"name\":\"mhl_run_resume\",\"arguments\":{\"runId\":\"$rid\",\"arguments\":{\"approved\":\"yes\"}}}}"
# structuredContent -> {"state":"working", ...}   then mhl_run_status -> {"state":"completed","vars":{ ... }}
ACROSS A RESTART

Start the server with --state-dir <dir> (or MHL_SERVE_STATE_DIR) and a later process pointed at the same directory can mhl_run_status / mhl_run_resume a runId it never started — the first caller to name the (unguessable) id reclaims it. Without it, run state is per-process and lost on restart. Checkpoints are one small JSON file per completed step, sized by the pipeline's variable state; mhl_run_status on a live run stays a pure in-memory read.

07Resources: mhl:// introspection

Executable

A tools/list entry is deliberately compact — name, description, inputSchema. The detail lives in read-only MCP resources, each a mhl:// URI you fetch with resources/read:

URIMIMEBody
mhl://workflow/<name>application/jsonmanifest — ordered steps, typed inputs, inputSchema, checkpoint, parallelGroups, stepTimeouts, loop, and the declared agents/tools/memory/prompts/extensions of its program
mhl://workflow/<name>/sourcetext/x-mhlthe declaration's .mh source
mhl://run/<runId>/logstext/plainthe run's retained step/log() output (HTTP only)
mhl://run/<runId>/resultapplication/jsonthe run's current status + final vars (HTTP only)
curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":3,"method":"resources/list"}'
# -> workflow manifest+source entries, plus one logs+result pair per async run you own

curl -s -X POST localhost:8711/mcp -H 'content-type: application/json' -H "Mcp-Session-Id: $sid" \
  -d '{"jsonrpc":"2.0","id":4,"method":"resources/read","params":{"uri":"mhl://workflow/Report"}}'
# -> { "contents": [ { "uri": "...", "mimeType": "application/json", "text": "{ \"steps\": [...], ... }" } ] }
DERIVED

The manifest is projected from the loaded pipeline, so it never drifts from what runs. The workflow resources are available over stdio and HTTP; the mhl://run/* ones need the run registry, so they are HTTP-only and owner-gated exactly like mhl_run_status (a non-owner sees unknown resource). mhl_run_start's result also carries resource_link items pointing at the new run's logs and result.

08A2A skills over HTTP

Executable

mhl serve a2a [--addr host:port] <dir> publishes one A2A skill per declaration: JSON-RPC 2.0 over HTTP, with an Agent Card at /.well-known/agent-card.json. message/send starts a run as a task; tasks/get polls it and tasks/cancel stops it. The skill and inputs are named explicitly in the message metadata.

Start the server, discover it, and send a task

mhl serve a2a --addr 127.0.0.1:8710 sample/serve &

curl -s localhost:8710/.well-known/agent-card.json

curl -s -X POST localhost:8710/ -d '{"jsonrpc":"2.0","id":1,"method":"message/send",
  "params":{"message":{"role":"user","parts":[],
    "metadata":{"skill":"Triage","input":{"title":"db outage","body":"prod is down"}}}}}'
# -> { "result": { "id": "<task-id>", "status": { "state": "submitted" }, ... } }

curl -s -X POST localhost:8710/ -d '{"jsonrpc":"2.0","id":2,"method":"tasks/get","params":{"id":"<task-id>"}}'
# -> status.state "completed", artifacts[0].parts[0].text = the run's result JSON
NOTE

A2A reports the task's lifecycle state (submitted / working / completed / failed / canceled), not the current step. For step-by-step progress or a resumable gate, use the MCP HTTP mhl_run_* tools above.

09Wiring a client

Executable

Point any MCP client at the command (stdio) or the URL (HTTP).

Networked client

# networked
claude mcp add --transport http mhl-local http://127.0.0.1:8711/mcp

Stdio client configuration

{
  "mcpServers": {
    "mhl-workflows": {
      "command": "mhl",
      "args": ["serve", "mcp", "/absolute/path/to/sample/serve"]
    }
  }
}

HTTP surface — drive it all with tools/call; the bracketed run/* is the raw JSON-RPC method a policy gateway can match by name

CallargumentsReturns
tools/list—one entry per workflow (+ the mhl_run_* tools), each with its inputSchema
tools/call <workflow>{…workflow inputs}blocks; the final variable state (isError on failure)
tools/call mhl_run_start (raw: run/start){workflow, arguments}{runId, state:"working"} at once; text + resource_links to the run's logs/result
tools/call mhl_run_status (raw: run/status){runId}{state, step, reached, vars?, error?, resumable?} as structuredContent
tools/call mhl_run_resume (raw: run/resume){runId, arguments?}relaunch from the checkpointed step; arguments merged over the originals
tools/call mhl_run_cancel (raw: run/cancel){runId}stop the run; its status
tools/call mhl_run_list (raw: run/list){}the calling session's own runs
tools/call mhl_run_logs (raw: run/logs){runId, since?}{text, nextSince, dropped?} — the run's retained step/log() output
resources/list—workflow manifest+source entries, plus a logs+result pair per async run you own
resources/read{uri}{contents:[{uri, mimeType, text}]} for a mhl://workflow/… or mhl://run/… URI
!
One trust domain per server

--token is a single shared secret — every holder is equally privileged, exactly like tools/call. Per-session ownership scopes run/* within a running process, but is best-effort across a restart (possession of the runId re-establishes it). Keep a --state-dir readable only by the server user, and bind to loopback unless a token is set.
