Passo a passo

O que "do zero" significou nesta rodada

Não foi um restart. Foi kubectl delete -k . (o namespace inteiro e tudo dentro dele), docker compose --profile runtime --profile observability down -v (Postgres, Keycloak, Floci, WireMock — sem volumes sobrando), as três imagens :local removidas e reconstruídas com --no-cache. O runtime agora vem de ./runtime/build.sh, que empacota os binários Linux já congelados em src/frozen/ (FREEZE.json sobre o commit b76ed72 mais as mudanças da árvore de trabalho) — não há mais go build no caminho da imagem. Depois: dependências no ar, kubectl apply -k ., rollout aguardado, e os 6 cases funcionais rodados de ponta a ponta antes de medir qualquer coisa.

# limpeza
kubectl delete -k .
docker compose --profile runtime --profile observability down -v
docker rmi -f mhl-runtime:local mhl-authorizer:local mhl-admissor:local

# reconstrucao (runtime = binarios congelados de src/frozen/)
./runtime/build.sh --no-cache
docker build --no-cache -f authorizer/Dockerfile -t mhl-authorizer:local authorizer
docker build --no-cache -f admissor/Dockerfile  -t mhl-admissor:local  admissor

# subida
docker compose --env-file .env -f docker-compose.yml --profile observability up -d
kubectl apply -k .
kubectl -n mhl-insurance-lab rollout status deployment/mhl-runtime --timeout=180s
for c in scripts.mh/case-0*.mh; do mhl run "$c"; done      # 6/6

# carga
INTERVAL=2 ./load-watch.sh        # CPU/memoria por container
SEGUNDOS=310 ./queue-probe.sh     # fila interna do runtime, 1 Hz
VUS=12 DURATION=240 SCENARIO=start RATE=6 ./load-test.sh

Confirmado: mhl version reporta mvp-b76ed72-1bb8661f5cf0 (não uma versão de release), a admission_queue foi recriada do zero pelo admissor no primeiro boot (CREATE TABLE IF NOT EXISTS em schema.sql), e a borda responde 401 sem token / 200 com token.

Diferenças em relação à baseline de 05/09

Mesma carga, runtime diferente

A versão do runtime mudou de patched-local-20260905 para mvp-b76ed72-1bb8661f5cf0

A baseline anterior compilava o runtime da fonte com -X …cli.Version=patched-local-<data> e um --build-context apontando para o checkout de mhl-runtime. O Dockerfile.local-patch foi desde então substituído: hoje o build só copia os binários de src/frozen/ e confere os SHA256SUMS do snapshot. O patch de separação checkpoint/status continua presente — está entre as mudanças de árvore de trabalho registradas em FREEZE.json (internal/mcpserver/runs.go, runlog.go, runlock.go, execsvc/inspect.go) — mas o número de versão agora identifica o snapshot, não a build local.

Config do admissor também difere: esta subida usa ADMIT_RATE=4.5, RECONCILE_GRACE=60 e RECONCILE_INTERVAL=15 (a baseline citava STALE_NONTERMINAL_SECONDS=120, variável que não aparece mais neste deployment).

load-test.sh deixou de contar o backpressure state=queued

O resumo do load-test.sh tem uma seção "backpressure declarado pelo servidor" que se apoia em grep -q ' queued$' sobre samples.txt. Desde que a coluna epoch passou a ser o último campo de cada linha, esse ancoramento em fim de linha nunca casa, e a seção some silenciosamente do relatório. Nesta rodada 96,6% das respostas (1.345 de 1.392) traziam queued no corpo — número extraído direto da coluna 4 de samples.txt, não do resumo do script. Pendência: trocar o padrão para $4 == "queued".

A fila interna do runtime nunca passou de 5 runs enfileirados (média 0,9) e 11 em execução simultânea (média 8,6) — o teto efetivo é 10 (5 por réplica × 2), e os 11 são um overshoot breve. Muito abaixo de qualquer risco de perda em queda de pod, o mesmo padrão dos chaos tests anteriores. Nem CPU (pico 6,5% de 1 core), nem memória (pico 30 MiB contra request de 128 MiB), nem a fila do runtime chegam perto de qualquer limite configurado. Vale uma ressalva: a memória do runtime subiu de ~21 para ~30 MiB ao longo dos 240 s — folga enorme ainda, mas uma inclinação positiva numa janela curta é exatamente o que um soak de 1 h precisa medir antes de descartar como ruído de warm-up.

Nenhuma das taxas varridas (2 a 20/s) fez a fila crescer na janela de 45 s — o pico máximo foi 3 runs, a 20/s. Isso quase certamente diz que a janela é curta demais para revelar o teto, não que 20/s é sustentável de verdade: a calibração da série anterior só viu crescimento a partir de ~6/s num soak de 1 h. O ponto de equilíbrio real deste runtime frozen continua sem medição de janela longa. O critério de "cresce" é fim > 2× início + 20, e a fila fim nunca passou de 0,4 em média. Para achar o ponto em que a taxa de chegada excede o que as 2 réplicas concluem (MHL_SERVE_MAX_CONCURRENT_RUNS=5 cada, chamadas HTTP reais de 200–500 ms) é preciso ou uma janela bem mais longa por taxa, ou taxas acima de 20/s.
