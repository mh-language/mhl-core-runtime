Passo a passo

O que "do zero" significou de verdade

Não foi um restart. Foi: kubectl delete -k . (derruba o namespace inteiro e tudo dentro dele), docker compose down -v (Postgres, Keycloak, WireMock, Floci — sem volumes sobrando), as três imagens :local removidas e reconstruídas sem cache, o binário do runtime recompilado da fonte com o patch já aplicado. Depois: dependências no ar, kubectl apply -k ., rollout aguardado, e só então os 6 cases funcionais do RUNBOOK rodados de ponta a ponta para confirmar que a base está sã antes de medir qualquer coisa.

# limpeza
kubectl delete -k .                                    # namespace inteiro
docker compose --profile runtime --profile observability down -v
docker rmi -f mhl-runtime:local mhl-authorizer:local mhl-admissor:local

# reconstrução (runtime compilado da fonte com o patch)
GOOS=linux GOARCH=arm64 go build ... -o dist/linux-arm64/mhl ./cmd/mhl
docker build -f runtime/Dockerfile.local-patch -t mhl-runtime:local \
  --build-context mhlsrc=../../mhl-runtime .
docker build --no-cache -f authorizer/Dockerfile -t mhl-authorizer:local authorizer
docker build --no-cache -f admissor/Dockerfile -t mhl-admissor:local admissor

# subida
docker compose --env-file .env -f docker-compose.yml up -d
kubectl apply -k .
kubectl -n mhl-insurance-lab rollout status deployment/mhl-runtime --timeout=180s
./run-all.sh                                            # 6/6 cases

Confirmado: mhl version reporta patched-local-20260905 (não uma versão de release), o admission_queue foi recriado do zero pelo próprio admissor no primeiro boot (CREATE TABLE IF NOT EXISTS em schema.sql), e a borda responde 401 sem token / 200 com token, como esperado.

Um tropeço no próprio ferramental

A primeira tentativa de carga "falhou" — mas não como parecia

9 de 12 VUs marcados como falha, na primeira rodada (descartada)

A primeira tentativa usou SCENARIO=mixed, que — fora do laço cronometrado — dispara um mhl_run_start síncrono por VU logo após abrir sessão, via lab_run_start em lib.sh, e exige um runId imediato na resposta (jq -er '.runId'). Com 12 VUs disparando essa chamada praticamente ao mesmo tempo e o admissor limitando a admissão a ADMIT_RATE=4.5/s, várias dessas chamadas voltam como queued_durable — aceitas e gravadas de forma durável, mas sem runId ainda. O harness trata a ausência de runId como falha fatal do VU. Não é um bug do admissor nem do runtime: é o ferramental de teste, escrito antes do admissor existir, que não sabe esperar por queued_durable.

Reproduzido isoladamente: 12 sessões abertas em paralelo contra o Keycloak/ authorizer funcionam 12/12 sem problema — o gargalo é especificamente a suposição de "runId síncrono" no caminho de mhl_run_start. A rodada válida usada neste relatório troca para SCENARIO=start, que já trata qualquer HTTP 200 (com ou sem queued no corpo) como sucesso — o comportamento correto agora que o admissor está na frente.

Pendência registrada: atualizar lib.sh/load-test.sh para os cenários status/mixed saberem seguir um claim_id através de queued_durable até um runId aparecer, em vez de tratar isso como erro. Sem essa correção, esses dois cenários não são confiáveis com o admissor em produção.
