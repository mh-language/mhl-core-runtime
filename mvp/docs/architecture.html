Regulação de sinistros, do evento à decisão.

O runtime MHL publica um workflow declarativo por MCP sobre HTTP. Um gateway NGINX valida o JWT do cliente na borda, o workflow consulta sistemas de seguros simulados, os checkpoints vivem no PostgreSQL e a decisão pode parar para revisão humana e ser retomada depois — inclusive em outra réplica.

01

Caminho de uma requisição

O JWT do usuário só existe na borda. O NGINX pergunta ao authorizer se o token é válido, recebe de volta o principal derivado e só então fala com o admissor — usando uma credencial interna que o cliente nunca vê. O admissor é quem fala com o runtime, e só ele.

  1. 1Login — o participante pega um JWT do usuário sintético no realm do Keycloak.
  2. 2Chamada — POST /mcp no gateway com Authorization: Bearer <jwt>.
  3. 3Subrequest — o NGINX chama /_auth (interno) sem repassar o corpo.
  4. 4Validação — o authorizer confere assinatura, iss, aud e exp com o JWKS em cache.
  5. 5Principal — resposta 200 devolve X-Mhl-Principal e, quando existe, X-Mhl-Lob.
  6. 6Proxy — o gateway troca o Authorization pelo MHL_TOKEN interno e injeta o principal, e passa a falar com o admissor, não mais com o runtime.
  7. 7Admissão — mhl_run_start é gravado em admission_queue antes de qualquer tentativa no runtime, e admitido a ADMIT_RATE; mhl_run_status aceita claim_id e responde da fila enquanto não há runId. Todo o resto passa pelo admissor sem alteração.
Regra de confiança: o cliente não escolhe sua identidade. Qualquer X-Mhl-Principal enviado por ele é descartado e substituído pelo valor que o authorizer devolveu, e o MHL_TOKEN nunca sai da rede interna — é a credencial que o admissor e o runtime exigem. O worker de admissão em segundo plano tem a sua própria cópia do MHL_TOKEN (mesmo segredo, mhl-runtime) porque retenta sem uma requisição de cliente por perto; mesmo assim o dono do run continua sendo o principal de quem pediu.
Por que o admissor existe: testes de chaos em 2026-09-05 mostraram que um run aceito (HTTP 200, com runId) mas ainda não puxado da fila interna some se o pod que o aceitou morrer — 436 runs perdidos num crash abrupto, 1.844 num rolling restart (o caminho de deploy recomendado no próprio RUNBOOK). mhl_serve_runs_queued é estado em memória, por pod; não sobrevive à réplica que o guarda. O admissor grava a intenção em admission_queue (Postgres) antes de tentar admitir. Um reconciliador roda a cada RECONCILE_INTERVAL (15 s) e, para um run admitted parado em queued/working há mais de STALE_NONTERMINAL_SECONDS (120 s), devolve a linha para pending — com um novo runId na próxima tentativa. Ver src/docker/admissor/admissor.py.
Um bug que moldou o desenho — mhl_run_status de run completado, com 2+ réplicas: na versão anterior, um run que completava tinha o registro em memória e o status publicado apagados na hora. Perguntar pelo Service balanceado mhl-runtime tinha 1/N de chance de cair na réplica que executou o run; as outras N−1/N respondiam "unknown runId" para um run perfeitamente bem-sucedido — confirmado ao vivo, pod a pod, com o mesmo runId. O patch de 2026-09-05 no runtime resolveu na origem: o status de um run terminal fica no store até um sweep por TTL, então qualquer réplica responde "completed" de forma consistente. Um Service headless (mhl-runtime-headless, clusterIP: None) foi o paliativo enquanto o patch não existia — viveu um dia e foi removido (ver o comentário em k8s/mhl-service.yaml). O que o patch não cobre — um run queued/working cujo pod morre e mantém essa string para sempre — é justamente o que o reconciliador do admissor trata por obsolescência.

Workflow RegulateClaim

Quatro passos de apuração, uma decisão e dois desfechos. A rota humana é o motivo de existir o store: o run para em pause(), o estado sobrevive e a retomada pode acontecer em outro processo.

PassoO que fazChamada externaDetalhe
IntakeCarrega o sinistro e a apólice.GET /claims/{id} · GET /policy/{id}timeout do passo: 15s
ExtractEvidenceResume as evidências dos documentos via agente.GET /documents/{id}timeout 30s · cache de agente 10min
AntiFraudObtém o score de fraude do caso.GET /antifraud/{id}timeout 15s
RouteEscolhe entre liberar direto ou mandar para revisão.—claim_amount ≤ 5000 && confidence ≥ 0.9 && fraud_score < 0.2
HumanReviewPausa o run até o regulador aprovar.—pause() quando approved != "yes"
RegisterRegistra o pagamento e grava a trilha de auditoria.POST /paymentsX-Idempotency-Key: claim:{id} · ClaimsAudit jsonl
Por que idempotência importa aqui: a mesma run pode ser retomada mais de uma vez depois de uma pausa ou de uma troca de réplica. A chave claim:{claim_id} é o que impede o laboratório de pagar o mesmo sinistro duas vezes — o mock payment-missing-idempotency.json existe para demonstrar a falha quando ela some.

06

Limites da simulação

O laboratório é fiel no formato das decisões, não na infraestrutura que as sustentaria em produção.

O que não está representado: EKS multi-AZ, IAM/IRSA, KMS, VPC, ALB, alta disponibilidade regional e requisitos de compliance. Keycloak, authorizer, NGINX, WireMock, Floci e PostgreSQL existem para tornar o treinamento executável em um notebook. A autorização de quem pode aprovar um sinistro também está simplificada: em produção ela pertence ao gateway ou ao mesh, não ao workflow.
O HPA é decorativo no Docker Desktop: sem metrics-server, kubectl top pod responde "Metrics API not available" e o HPA fica em cpu: <unknown>/70% — nunca escalou em nenhuma rodada de carga. As replicas: 2 são fixas na prática; o objeto HPA está no manifesto para mostrar a forma, não para exercê-la. O rate-limit real da vazão é o ADMIT_RATE de uma única réplica do admissor (token bucket em memória — daí replicas: 1 e strategy: Recreate).
