Architecture note

MHL MCP Server on EKS

A target design for exposing the mhl documentation workflow to many AWS teams through an authenticated API Gateway — and the points where the runtime, as written today, does not yet hold up under that load.

scope: mhl serve mcp --http transport: Streamable HTTP (POST /mcp) refs: internal/mcpserver, internal/execsvc status: tests_mcp_pods 18/18 + tests_ext 21/21 — 2026-08-31

The scenario

One documentation workflow, written in .mh, is run every day by several product teams. Each team lives in its own AWS account, reaches a shared regional API Gateway endpoint, authenticates there, and the request is forwarded privately into an EKS cluster where the mhl server runs as a Deployment of several pods behind a load balancer.

The workflow is long: it fans out to LLM calls and, for a documentation pipeline, almost certainly includes a human approval gate before anything is published. That makes it a natural fit for the server's async run/start → run/status → run/resume extension rather than a single blocking tools/call.

Load shapeBursty. Many teams trigger the same pipeline in the same morning window; each run is minutes long and spawns sub-agents.
IdentityTeams are distinct principals. Runs, logs and approvals must not cross team boundaries.
IngressAPI Gateway is the only door and does the real authentication (Cognito / Lambda authorizer / SigV4).
RuntimeStateless-looking pods, rotated by deploys and the HPA. Anything a run needs to survive a pod must live outside the pod.

Target architecture

The request path is conventional AWS. What matters for mhl are the marked edges — each is a place where the implementation once assumed a single process on one machine. Three are now closed and test-verified (green); one dashed edge remains: pod affinity for the live session and run registry.

AWS-side choices (uncontested)

  • API Gateway HTTP API with a JWT authorizer (Cognito or the team IdP), private integration over a VPC Link to an internal ALB managed by the AWS Load Balancer Controller.
  • EKS Deployment, HorizontalPodAutoscaler on CPU plus a custom “in-flight runs” metric, PodDisruptionBudget so drains are staggered.
  • IRSA for the pod service account — read access to the specific Secrets Manager paths holding LLM keys, and (proposed) to the run-state table.
  • Egress to the LLM provider via NAT Gateway, or a Bedrock VPC endpoint if the workflow's agents target Bedrock.
  • Observability: ADOT sidecar / collector → CloudWatch Logs + Amazon Managed Prometheus; per-team, per-workflow dashboards for usage and cost.

What one documentation run looks like

The human-in-the-loop pattern the server already supports: a gate step calls fail() until approved, then run/resume merges the decision in. Every hop below crosses a pod boundary — and, with the shared --state-dir / store, each one now works: the session resolves on any pod, run/status reads a live run-status, and the run is bound to its owner. Only “who may approve” stays outside the runtime.

Where MHL needs work

Ordered by whether the scenario functions without the change. P0 blocks it, P1 is required for production quality, P2 is a real improvement that can wait. Cada item traz agora um chip de status (atendido parcial aberto fora do runtime) e a linha Verificado.

01 Async run state is node-local P0 atendido

Today
In internal/mcpserver/runs.go, a run's checkpoint tree lives under h.runsDir (a per-process temp dir, or a single --state-dir path), and the h.runs registry, its cancel func and the executing goroutine are in-memory on one pod.
Breaks here
With replicas, run/status / run/resume / run/cancel routed to another pod hit reconstructRun, which sees only committed checkpoints — no live step progress, and no way to cancel a goroutine on a different pod. A shared --state-dir on EFS fixes disk but not the registry or the cancel signal.
Direction
A StateStore interface (list / get / put / claim / watch) with the current disk code as one implementation and DynamoDB or Redis as another; a distributed cancel (store a cancelRequested flag the owning pod polls at each step boundary) or explicit run affinity.
Verificado
O seam StateStore / CheckpointStore / SessionStore existe e roteia por um extension store. Além do disco (--state-dir, CENARIO-011), há dois backends de produção verificados ponta a ponta com mhl serve mcp --http: S3 (src/mhl-extensions/mhl-store-s3 — cliente SigV4 sem dependências, retry com backoff, credenciais IRSA AssumeRoleWithWebIdentity / IMDSv2) e PostgreSQL (src/mhl-extensions/mhl-store-postgres — INSERT ... ON CONFLICT DO UPDATE). Com extension store S { ... } no dir de workflows, session/*, run/<id>/checkpoint/* e o owner vão para o backend; um segundo processo no mesmo bucket/tabela reconstrói a run e run/resume chega a completed; run/start concorrentes gravam chaves disjuntas (CENARIO-013 / CENARIO-016). Pendente: o registro live (h.runs, goroutine, cancel) multi-pod e o cancel distribuído — o store não carrega o progresso em memória.

02 MCP sessions live in one pod's memory P0 atendido

Today
h.sessions in http.go is behind the SessionStore seam. With --state-dir it is diskSessionStore (one JSON per Mcp-Session-Id under .mhl/state/sessions/); with an extension store declared it is extSessionStore (keys session/<sid> on the backend); with neither, the process-local memSessionStore.
Breaks here
Solved for the shared-storage deployment: round-robin across pods no longer misses the session — any replica pointed at the same --state-dir (or store) resolves an id minted by another, with no forced re-initialize. The stateless params._meta form's ownerKey="" is closed by --principal-header (item 03), where ownership is the identity hash, not the session.
Direction
Done: sessions sit behind the same seam as run state. A routing contract (stable client key + ingress hash-route) was the alternative; the store path won — an ALB cannot key on a body field.
Verificado
tests_mcp_targets/ITEM-02 → MET: tools/list no Pod B com um Mcp-Session-Id cunhado no Pod A → 200; run/start no A + run/status no B com a mesma sessão funciona; e (regressão) com --principal-header o bob no Pod B não vê a run de alice iniciada no Pod A (-32602), alice vê. Cobertura Go: TestHTTPSharedSessionsAcrossReplicas, TestDiskSessionStoreSharesAcrossInstances. Backend externo: session/<sid> num extension store (CENARIO-013 / CENARIO-016).

03 No caller identity reaches the runtime P0 atendido

Today
The only credential the server understands is one static bearer token (--token / MHL_SERVE_TOKEN), checked for equality in handleMCP. Run ownership is sha256(Mcp-Session-Id) — possession of a self-minted id, not an identity.
Breaks here
Every team arrives behind API Gateway with the same upstream token, so run/list and resumable runs are shared across teams. The loopback-Origin guard is meaningless behind an ALB.
Direction
Accept a principal from a trusted header (--principal-header X-Mhl-Principal, populated by the API Gateway authorizer) or validate a JWT against JWKS directly; key ownership, memory scoping and log access on that principal.
Verificado
Implementado como a variante trusted-header. Com --principal-header X-Mhl-Principal + --token, o owner de uma run é ownerFor(principal) (hash da identidade verificada): bob não vê nem toca a run de alice (run/list vazio, run/status → -32602), e o servidor recusa --principal-header sem --token (CENARIO-006). Guard de bearer/Origin em CENARIO-005. JWT/JWKS direto continua em aberto (item 10).

04 tools/call blocks for the whole run P0 fora do runtime

Today
callTool in server.go holds the HTTP request open through execsvc.Run. The async run/* methods are the escape hatch.
Breaks here
API Gateway's integration timeout is ~29 s and the ALB idle timeout defaults to 60 s; a real documentation run exceeds both. A stock MCP client that only knows tools/call will always time out.
Direction
Fora do runtime. Não é distribuição nem isolamento — é ergonomia de gateway. O contrato: atrás do API Gateway o cliente usa run/start → run/status → run/resume, e a capability experimental["mhl.run"] (item 11) torna isso descobrível. Um auto-promote de tools/call pode entrar depois como conveniência, mas não como pré-requisito do cenário.
Verificado
A superfície assíncrona — run/start → poll run/status → run/resume no gate → completed — funciona ponta a ponta (CENARIO-007), e um tools/call síncrono com o pool cheio devolve -32000 apontando run/start (CENARIO-008). Registro do gap de auto-promote em _delegated/ITEM-04.

05 No server-level concurrency limit or queue P1 atendido

Today
run/start and tools/call launch a run unconditionally. The only ceiling is per-pipeline spawn.MaxConcurrency for sub-agents (execsvc.go).
Breaks here
A synchronized morning burst across teams multiplies into hundreds of concurrent LLM calls — pod OOM, fd exhaustion, and a provider 429 storm with no shed load.
Direction
--max-concurrent-runs with a weighted semaphore, a bounded queue, and a first-class queued run state so clients poll instead of retrying. Export the in-flight gauge for HPA.
Verificado
Com --max-concurrent-runs 1: 3× run/start → working, queued (queuePosition 0/1); tools/call em capacidade máxima → -32000 server at capacity após ~5 s; run/cancel numa run queued a descarta sem executar; a fila anda quando o slot libera. Gauges mhl_serve_runs_active / runs_queued refletem o estado (CENARIO-008, CENARIO-012).

06 No health or readiness endpoints P1 atendido

Today
The mux registers only /mcp (POST / DELETE). There is no /healthz or /readyz.
Breaks here
Kubernetes has nothing to probe; it cannot tell a starting pod from a ready one, and cannot be told to stop routing to a draining pod.
Direction
Add GET /healthz (liveness) and GET /readyz (flips to unready on SIGTERM, before the drain window starts).
Verificado
GET /healthz e /readyz respondem 200 sem bearer (assim como /metrics), enquanto POST /mcp continua 401 (CENARIO-004). No SIGTERM, /readyz vira 503 antes do dreno e /healthz fica 200 (CENARIO-009); sob kubelet real o IP do pod sai dos Endpoints do Service (CENARIO-K8S-001).

07 Shutdown cancels in-flight runs after 5 s P1 atendido

Today
On SIGTERM the server context is cancelled — every async run's context ends at the next step boundary — and httpSrv.Shutdown gets a hard 5 second window (http.go).
Breaks here
Routine pod rotation (deploys, HPA scale-in, node drain) kills running documentation builds. They survive only if the workflow happened to declare checkpoint { strategy: "per_step" }.
Direction
A configurable drain timeout; “stop accepting new runs, let in-flight ones finish”; and write a checkpoint on shutdown regardless of the declared strategy so any run is resumable.
Verificado
Com --drain-timeout 20s: no SIGTERM a run em andamento continua (Compile→Package→Ship) e termina sozinha; o processo só encerra depois (~6 s), run/start responde -32000 server is draining, e o stderr registra a linha JSON draining. Um restart no mesmo --state-dir mostra a run como resumable mesmo SlowBuild não declarando per_step (checkpoint de shutdown). --drain-timeout 0 mantém o corte imediato (CENARIO-009; sob kubelet real em CENARIO-K8S-001). Nota: um defeito foi achado e corrigido — runsCtx era filho do contexto de sinal, então o SIGTERM cancelava a run por propagação de contexto antes de o dreno esperar; agora runsCtx := context.WithCancel(context.WithoutCancel(ctx)).

08 Unstructured diagnostics, no metrics P1 atendido (núcleo)

Today
All output is free text to a single syncWriter over stderr (logw). No request counts, run durations, error rates, token or cost counters; no trace or runId correlation.
Breaks here
“Which team is spending what, and what's failing” — the first questions a daily multi-team service raises — are unanswerable.
Direction
Structured JSON log lines keyed by runId and principal; an OTLP exporter or /metrics with in-flight, duration, outcome, and per-workflow token/cost series.
Verificado
GET /metrics (texto Prometheus, sem auth): mhl_serve_runs_total{outcome}, run_duration_seconds_{sum,count}, tool_calls_total{ok|error}, gauges runs_active/runs_queued/sessions_active — os valores acompanham a atividade (CENARIO-012). O stderr emite linhas JSON run started/run completed com runId + owner (CENARIO-013). Pendente: exporter OTLP / tracing e séries token+custo por workflow.

09 Per-run logs are not retrievable P1 atendido

Today
execRun sends a run's log() / step output to the shared server sink. run/status returns step names and final vars only.
Breaks here
A team whose run failed cannot see why through the API; an operator has to grep pod stdout and correlate by hand.
Direction
Capture per-run output (ring buffer in the state store) and add run/logs { runId, since }, principal-scoped.
Verificado
run/logs { runId } devolve { text, nextSince } com a saída step: da run; a releitura com since: nextSince volta vazia e com o cursor estável; outra sessão recebe -32602 unknown runId (owner-scoped). Ring de 64 KiB (CENARIO-013).

10 Auth is a single static token P1 delegado ao mesh

Today
One process-wide --token string, checked for equality. No JWT, no per-team tokens, no scopes, no rotation.
Breaks here
Only if the runtime is expected to do auth. It is not: the API Gateway / Istio validate the credential and inject the caller's identity; the runtime just needs to trust and partition on it.
Direction
Delegado ao mesh. Validação de JWT contra JWKS fica no Istio (RequestAuthentication) ou no API Gateway (Cognito / Lambda authorizer), que injeta o sub em X-Mhl-Principal. O runtime já faz sua parte: --principal-header (item 03) transforma essa identidade verificada no owner das runs, isolando run/list/run/status/run/logs/run/resume por principal — inclusive entre réplicas (item 02). O --token permanece só como o segredo compartilhado gateway↔mhl (anti-spoof do header).
Verificado
O isolamento por principal funciona (CENARIO-006); o guard 401/200 do --token também (CENARIO-005). O gap de auth-por-principal fica documentado, fora da lista de trabalho, em _delegated/ITEM-10.

11 run/* is a non-standard extension P2 atendido

Today
Sobre HTTP (o transporte que roteia run/*), initialize e server/discover devolvem capabilities.experimental["mhl.run"] = { "version": "1", "methods": ["run/start", "run/status", "run/resume", "run/cancel", "run/list", "run/logs"] }, e cada tool em tools/list ganha _meta.mhl.run = { async: true, via: "run/start" }. Sobre stdio, que não roteia run/*, o bloco experimental fica ausente. Clientes que ignoram experimental seguem funcionando.
Breaks here
Fechado para o cenário: um cliente descobre a família run/* e sua versão no handshake, em vez de precisar de código sob medida.
Direction
Acompanhar o mecanismo de progress-notification do MCP conforme estabiliza e migrar quando fizer sentido; hoje é uma extensão via experimental.
Verificado
initialize sobre HTTP → capabilities com as chaves experimental + tools; experimental["mhl.run"].version == "1" e os 6 métodos listados; tools/list traz o _meta.mhl.run; run/<bogus> → -32601 (sem regressão); stdio não anuncia experimental (tests_mcp_targets/ITEM-11 → MET; testes TestHTTPAdvertisesAsyncRunCapability + TestServeInitializeListCall; conformidade geral em CENARIO-014).

12 HITL gates have no approver authorization P2 isolamento atendido authz no mesh

Today
run/resume merges arguments over the run's inputs with no check beyond run ownership; after a restart, reconstructRun lets the first caller to name the (unguessable) runId claim it.
Breaks here
“Who may approve a doc for publication” is a core requirement the language cannot express; any owner can approve, and once runIds appear in logs or traces the reclaim path widens.
Direction
Duas metades. Isolamento (runtime): ligar a run ao principal para que só o dono a veja/retome — feito. Authz de aprovador (mesh): "quem pode aprovar" é uma AuthorizationPolicy do Istio em POST /mcp/run/resume (o wrapper POST /mcp/<method> isola esse path). approvers: não vira propriedade da linguagem.
Verificado
Isolamento: com --principal-header o owner é a identidade e é persistido (CheckpointStore.WriteOwner), então um não-dono recebe -32602 em run/status/run/resume, inclusive pós-restart e entre réplicas (CENARIO-006 / CENARIO-011 / ITEM-02). O gap de approvers: fica documentado, fora da lista de trabalho, em _delegated/ITEM-12.

Quick wins vs. bigger bets

Quick win — contained changeBigger bet — design work
feito GET /healthz + /readyz on the mux; unready on SIGTERM feito StateStore / CheckpointStore / SessionStore seams + backends de produção: S3 e PostgreSQL via extension store (CENARIO-013/016). Redis existe como kind cache
feito --drain-timeout; stop-accepting-then-drain instead of a 5 s hard stop feito registro live entre réplicas: run-status publicado por passo + flag cancel no store compartilhado (o cancel distribuído chega à goroutine da réplica dona). Sessões compartilhadas entre pods via diskSessionStore (--state-dir) / extSessionStore (ITEM-02)
feito Checkpoint on shutdown even without strategy: "per_step" ○ OpenTelemetry tracing + metrics, with per-team token and cost accounting
feito --max-concurrent-runs semaphore + a queued run state — delegado ao mesh: JWT/JWKS no Istio ou no API Gateway; o runtime só consome X-Mhl-Principal (item 03)
feito --principal-header feeding ownerKey instead of the session hash — delegado ao mesh: AuthorizationPolicy por path/principal; o isolamento por posse já é do runtime
feito JSON log lines carrying runId + principal ○ Auto-promote a long tools/call to an async run

The quick wins make a single-replica deployment behind API Gateway genuinely usable and observable. The scenario as described — several teams, every day, on an autoscaled Deployment — needs the left-hand column and a shared store for run and session state: without it, more than one pod is unsafe.

Situação (2026-08-31): a coluna esquerda inteira está entregue e verificada (tests_mcp_pods/ 18/18). Com o --state-dir compartilhado (ou um extension store), o multi-réplica está fechado: sessões e registro live de runs cruzam entre pods, e run/cancel alcança a réplica dona (ITEM-01/02). Falta só observabilidade: tracing/custo (OTLP). Auth (JWT/JWKS) e authz de aprovador (approvers:) ficam no service mesh.
