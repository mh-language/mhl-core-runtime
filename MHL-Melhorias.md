# Melhorias sugeridas para a linguagem MHL

> Feedback para quem mantém o compilador/runtime do MHL — não é trabalho do projeto Senpai. Cada item nasceu de um comportamento real observado (spike, `mhl lint`/`mhl run` real, ou uma lacuna de documentação) ao construir o Senpai em MHL `1.4.0-beta.5`, não de uma preferência abstrata. Referência cruzada: [FASE0-ACHADOS.md](FASE0-ACHADOS.md) tem o relato completo de cada spike citado aqui. Atualizar esta lista sempre que uma nova fase esbarrar em outra lacuna.

## 1. `agent.command`/`args` deveriam aceitar uma expressão, não só string literal — ✅ Resolvido

Hoje `command: env("VAR")` falha com `agent "X" has no command` — só uma string literal é aceita (confirmado em spike, [FASE0-ACHADOS.md §1](FASE0-ACHADOS.md#1-commandargs-do-agent-não-aceitam-env--só-string-literal)). Isso força qualquer produto que precise trocar de backend de LLM por ambiente (dev vs. produção) a manter arquivos `.mh` de agente **duplicados**, um por ambiente, escolhidos por qual é importado — em vez de uma única declaração parametrizada por `env(...)`/`context.*`. Permitir `command:`/`args:` avaliarem uma expressão (ainda que só no momento da declaração, não por chamada) removeria essa duplicação estrutural.

> **Status:** `command`/cada elemento de `args` agora aceitam qualquer expressão (`env(...)`, concatenação, variável), não só string literal — mesmo tratamento que `extension { endpoint: env(...) }` já tinha. Um literal de string continua sendo usado ao pé da letra (sem interpolar `${...}`), preservando os placeholders `"${prompt}"`/`"${schema}"`. Uma referência de credencial em `env(...)` falha fechado (mesma garantia de `extension`) e é registrada para redaction. `mhl lint` para de reportar falso "has no command"/"args must be an array" para uma expressão não-literal. Implementado em `internal/engine/interpreter/agent.go` (`resolveAgentCommand`/`resolveCommandLikeExpr`) e `internal/lang/ast/agentconfig.go`; testes em `agent_engine_test.go`, `lint_test.go`.

## 2. `mhl serve mcp` (stdio) deveria expor os mesmos `mhl_run_*` que o modo `--http` — 🚧 Blocking

Confirmado por spike: a variante stdio (`mhl serve mcp <dir>`) só publica os workflows como ferramentas síncronas — `tools/list` nunca inclui `mhl_run_start`/`status`/`resume`/`cancel`/`list`/`logs`, e chamá-los retorna `unknown tool`. Isso obriga qualquer aplicação desktop que só precisa de um processo filho local (sem nenhuma intenção de expor rede) a abrir uma porta HTTP em loopback só para ganhar acesso a progresso assíncrono e human-in-the-loop — que são conceitos de protocolo (MCP), não de transporte. Achado completo: [FASE0-ACHADOS.md §2](FASE0-ACHADOS.md#2-achado-crítico--mhl_run_startstatusresumecancellistlogs-só-existem-sob---http-nunca-em-stdio-puro).

**Sugestão:** publicar os `mhl_run_*` também sobre stdio (mesmo protocolo JSON-RPC, sem sessão HTTP) — o "dono" de um run em stdio seria naturalmente o único processo cliente do outro lado do pipe, então nem precisaria do conceito de `Mcp-Session-Id`.

## 3. `memory { path: "...${var}..." }` deveria ter um modo seguro contra path traversal — ✅ Resolvido

Confirmado por spike ([FASE0-ACHADOS.md §7](FASE0-ACHADOS.md#7-achado-crítico-de-segurança--memory--path--interpola-sem-sanitizar-path-traversal-funciona-de-verdade)): um `project_id` como `"../../../../tmp/x"` interpolado em `path: "projects/${project_id}/f.json"` escreve de verdade fora do diretório pretendido — a interpolação de `${...}` em `path:` não faz nenhuma validação. Isso é um footgun sério para qualquer app multi-tenant/multi-projeto construída em MHL (isolamento por diretório é um padrão comum). Hoje a única defesa é 100% do código do usuário (nosso `tool Paths`), nunca do runtime.

**Sugestão:** ao menos uma opção declarativa — `memory { path: "...", path_guard: "no_traversal" }` (ou equivalente) — que rejeite (`fail`) automaticamente um valor interpolado contendo `..` ou um caminho absoluto antes de tocar o disco. Não precisa ser o padrão (quebraria casos legítimos), mas hoje não existe nem como opt-in.

> **Status:** implementado exatamente como sugerido — `memory { path_guard: "no_traversal" }` (opt-in, não é o padrão). A checagem é por *span* interpolado (o valor de cada `${...}`), não na string final concatenada — assim um `path:` cujo template já começa de um diretório absoluto continua válido; só o segmento interpolado (ex. `project_id`) é barrado se contiver `..` ou tiver cara de caminho absoluto. Qualquer outro valor de `path_guard` é erro em tempo de lint. Implementado em `internal/engine/interpreter/memory_ops.go` (`memoryPath`/`guardPathSpan`) e `internal/engine/interpreter/interpolate.go` (`interpolateChecked`); testes em `memory_test.go` (cenário de traversal real bloqueado) e `lint_test.go`.

## 4. `html.escape`/`html.attr_escape` nativos — ✅ Resolvido

O bloco de operações nativas de `html` já tem `parse`, `get_element(s)`, `get_element_by_id`, `get_attribute`, `get_text`, `to_html` — mas nenhum `escape`. Qualquer geração de HTML a partir de texto de LLM (nosso caso de uso central em `Discovery`/`Delivery`) precisa reimplementar escaping à mão como uma cadeia de `.replace("&","&amp;").replace("<","&lt;")...`, na ordem certa, sem checagem do compilador de que a ordem/cobertura está correta. Isso é exatamente o tipo de operação que deveria ser nativa e testada pelo próprio runtime, do mesmo jeito que `json.stringify` já cobre escaping de string JSON.

> **Status:** `html.escape(text)` e `html.attr_escape(text)` implementados — os dois delegam para o escaping de `golang.org/x/net/html` (`<`, `>`, `&`, `'`, `"`), que já cobre tanto conteúdo de texto quanto valor de atributo entre aspas simples ou duplas; existem como dois nomes por clareza no call-site, não porque a regra de escaping seja diferente entre eles. Implementado em `internal/features/nativeops/html.go` (`EscapeHTML`) + `internal/engine/interpreter/tool.go`; catálogo do LSP atualizado; testes em `html_test.go` (Go) e `sample/features/html/html_escape_and_attr_escape.mh` (round-trip real: escapar, montar HTML, fazer parse de volta e comparar).

## 5. `mhl lint` tem falso-positivo em `<array-var>.append(x)` — ✅ Resolvido

`items.append(x)` numa `var` array simples (nunca declarada como `memory`) é sinalizado por `mhl lint` como `memory "items" not found` — o linter parece resolver `<nome>.append(...)` tentando primeiro achar uma declaração `memory` com esse nome (já que `memory { type: "append_log" | "jsonl" }` também expõe um método `append`), e erra quando não existe, mesmo o `mhl run`/`mhl test` executando o array `.append()` corretamente. Já existe um caso irmão documentado nos próprios docs oficiais (`json memory has no method "remove"` como falso positivo conhecido) — sugerimos tratar este da mesma forma: como um item de correção do lint, não do usuário. Achado completo com repro mínimo: [FASE0-ACHADOS.md §8](FASE0-ACHADOS.md#8-achados-de-sintaxe-descobertos-escrevendo-a-fase-1-tool-paths--workflow-workitem).

> **Status:** corrigido — antes de cair no fallback "memory not found" para um método que colide com nome de método de `memory` (`set`/`get`/`append`/`remove`), o lint agora checa se o alvo já é uma variável local conhecida (`var`/`const`/parâmetro/`spawn`/`for-in`) e, se for, não emite achado nenhum (é um método de valor comum, resolvido em runtime). Implementado em `internal/lang/lint/checks.go` (`checkExprCallShape`); teste `TestLocalArrayAppendNotFlaggedAsMemory` em `lint_test.go`.

## 6. Chamada de método-irmão dentro de um `tool` — ✅ Não era um gap: `self.` já resolve

Registrado inicialmente como bloqueio na Fase 1: dentro de `tool Paths { root(id) -> "projects/" + ensure_valid(id) }`, chamar `ensure_valid(id)` **sem nenhum prefixo** falha com `undefined variable "ensure_valid"`. Concluí, na hora, que só `Paths.ensure_valid(id)` (nome completo do tool) resolvia — e reportei isso como fricção da linguagem.

**Correção (Fase 2):** isso estava incompleto — eu nunca tinha testado `self.ensure_valid(id)`. Verificado por spike: `self.<metodo>(...)` funciona perfeitamente para chamar um metodo-irmao do mesmo `tool`, tanto em corpo de expressao (`a(): string -> self.b()`) quanto em bloco (`var x = self.b()`). Ou seja, a linguagem **já tem** o equivalente a `this.foo()` de outras linguagens — só não é documentado nas páginas de referência lidas (nenhum exemplo oficial usa `self.`), o que foi exatamente por que essa forma não apareceu na primeira tentativa. Rebaixado de "🚧 Blocking" pra uma lacuna só de **documentação**: vale a pena os docs oficiais mostrarem `self.` explicitamente no exemplo de `tool` (Docs-Reference §09), já que é a forma idiomática e evita reescrever o nome do `tool` toda vez (mais seguro a refactor — renomear o `tool` não exige tocar every call site interno).

**Ação nossa:** todo `tool` do Senpai passa a usar `self.<metodo>(...)` pra chamadas internas entre métodos-irmãos, não `NomeDoTool.<metodo>(...)` — mais limpo e mais resistente a rename (C7).

## 7. Escrita de campo de objeto via `.` (não só `[...]`) — 🚧 Blocking

Leitura funciona com `obj.campo`, mas escrita (`obj.campo = valor`) falha com `assignment target must be a plain variable or an array index, not a nested field` — é preciso `obj["campo"] = valor`. A assimetria entre leitura (ponto) e escrita (colchete) para o mesmo tipo de acesso é uma pegadinha discreta; poucos usuários vão adivinhar que `obj.campo = x` é rejeitado antes de tentar.

## 8. `input` de `pipeline`/`workflow` não aceita valor default — ✅ Resolvido

Só `parameter` (de `tool`/lambda) aceita `= expressão`; `input` é sempre obrigatório. Como cada `pipeline`/`workflow` vira uma ferramenta MCP com "every input required" (Docs-Servers §01), isso significa que um workflow com múltiplas ações (nosso `WorkItem`, por exemplo, com `create`/`list`/`get`/`archive`/`usage`) obriga o chamador a sempre passar **todos** os inputs em toda chamada, mesmo os irrelevantes para a ação escolhida (`item_type: ""` numa chamada `action: "list"`, por exemplo) — o esquema JSON exposto via `tools/list` também fica menos preciso (marca `item_type` como obrigatório mesmo quando é ignorado por 4 das 5 ações). Um `input x: Type = default` opcional deixaria tanto o `.mh` quanto o `inputSchema` derivado mais honestos sobre o que cada ação realmente usa.

> **Status:** `input name: Type = expr` agora é aceito, com a mesma sintaxe de `parameter`. Um input com default vira opcional: some do `required` do `inputSchema` derivado e, quando o default é um literal, aparece também como `"default"` no schema JSON. `ValidateInputs` não marca mais o input como `missing` quando ausente. A expressão do default é avaliada uma vez por execução (mesmo timing de um `var` de pipeline) e um valor explicitamente passado pelo chamador sempre vence sobre o default. Implementado em `internal/lang/ast/pipeline.go`, `internal/engine/runtime/pipeline.go` + `schema.go`, `internal/engine/interpreter/exec.go` (`EvalPipelineVars`); testes em `schema_test.go`, `execsvc_test.go`, `parser_test.go`.

## 9. Enums em `input` de workflow servido por MCP — ✅ Resolvido

Não testamos still, mas a tabela de "Declarable types" não deixa claro se um `input action: ActionType` (com `enum ActionType { Create, List, Get, Archive, Usage }`) é aceito e, se for, como isso se projeta no `inputSchema` JSON exposto via `tools/list` (JSON Schema tem `enum` nativo — seria o mapeamento natural). Se funcionar, seria a forma correta de fechar valores como `action`/`type` em vez de string livre + validação manual dentro do step. Vale um spike futuro dedicado; hoje é registrado aqui como lacuna de documentação, não como bug confirmado.

> **Status:** confirmado por investigação de código (não só spike): `input action: ActionType` já funcionava e já era aceito antes desta mudança, mas projetava no schema só como `{"type": "string"}` genérico — a lacuna real não era "funciona ou não", era a falta do `"enum": [...]` no JSON Schema. Corrigido: `runtime.FindPipeline` agora resolve os variants declarados do `enum` e `InputSchema()` os inclui como `"enum": ["Create", "List", ...]`, na ordem de declaração — o mapeamento nativo do JSON Schema que o item já esperava. Implementado em `internal/engine/runtime/pipeline.go` (`enumVariants`, `PipelineInputSpec.EnumVariants`) e `schema.go`; testes em `schema_test.go` (unit + end-to-end via `FindPipeline` com `enum` real).

## 10. `time.format`/`time.parse` — escapar literais nos tokens amigáveis (`yyyy`/`MM`/…) — 🚧 Blocking

O layout "amigável" (`yyyy-MM-dd`) não tem mecanismo de escape para caracteres literais no meio do padrão — `"yyyy-MM-dd'T'HH:mm:ss'Z'"` (sintaxe de aspas simples do Java/ICU) produz literalmente as aspas na saída em vez de tratar `T`/`Z` como literais. Hoje o único jeito de conseguir um timestamp ISO 8601/RFC 3339 correto é abandonar os tokens amigáveis e usar o layout Go puro (`"2006-01-02T15:04:05Z07:00"`) — o que exige conhecer a convenção de referência do Go (`Mon Jan 2 15:04:05 MST 2006`), justamente o conhecimento que os tokens amigáveis deveriam evitar exigir. Um mecanismo de escape (aspas simples, como ICU, ou colchetes) fecharia essa lacuna sem quebrar compatibilidade.

## 11. Contrato de saída estruturada (`schema:`) deveria ser uniforme entre adapters `cli/*` — 🚧 Blocking

Hoje, na prática (não documentado, descoberto testando os três CLIs reais):
- `claude`: `--json-schema <schema-inline>` — schema como string JSON direta no argv.
- `codex`: `codex exec --output-schema <arquivo>` — schema como **caminho de arquivo**, não inline.
- `devin`: **nenhuma flag de saída estruturada** em `--help`/`-p`.

Um usuário que declara `agent.run(prompt:, schema:)` esperando o mesmo comportamento documentado ("passed to backends that support structured output") precisa descobrir por tentativa que `codex` exige gravar o schema em disco antes da chamada, e que `devin` simplesmente não tem como cumprir o contrato via CLI nenhuma. Se o adapter `cli/*` do MHL abstraísse essas diferenças (escrevendo o arquivo temporário sozinho quando o CLI exigir um caminho, e falhando de forma clara e antecipada — não silenciosa — quando o CLI não suportar nada), `schema:` seria de fato portável entre backends, como o texto da documentação sugere que já é.

**Reverificado (após a Fase 3):** vasculhado de novo, desta vez todo subcomando do `devin` (`acp`, `mcp`, `auth`, `models`, `rules`, `skills`, `plugins`, `cloud`, `sandbox`, `setup`), não só `--help`/`-p` de primeiro nível — continua sem nenhuma flag de `schema`/`json`/`output-format`/`structured` em lugar nenhum. `devin acp` (Agent Client Protocol) foi o único candidato remotamente relacionado por ser JSON-RPC, mas é um protocolo de integração com editor (ações do agente, permissões), não um mecanismo de saída estruturada de propósito geral. Confirma que este item não é uma lacuna pontual de documentação — é ausência real de funcionalidade no CLI do Devin hoje.

## 12. `mhl run --format json` pode emitir JSON tecnicamente inválido — 🚧 Blocking

O campo `log` do envelope de saída às vezes contém quebras de linha reais (não escapadas como `\n`) dentro do valor da string, o que faz um parser JSON estrito (`json.loads` do Python, por exemplo) rejeitar o documento inteiro com "Invalid control character". Um consumidor programático de `--format json` (o próprio caso de uso do flag) não deveria precisar de um parser tolerante a JSON malformado.

## 13. Testar um `pipeline`/`workflow` inteiro (steps + `goto` + `pause`) de dentro de `test`/`describe` — 🚧 Blocking

O bloco `test`/`describe` hoje só exercita `tool`s e expressões — não há um jeito documentado de rodar um `workflow` inteiro (com seus `step`s, `goto`s e `pause()`s) a partir de um `test`, validando `reached`/`state` como se faz manualmente via `mhl run --format json`. Isso deixa um buraco de cobertura automatizada: hoje a única forma de testar o *fluxo* de um `workflow` (não só a lógica pura dentro de um `tool`) é rodar `mhl run` de verdade e inspecionar a saída manualmente/via script externo, fora do framework de teste nativo do MHL.

## 14. Suporte a classes de caracteres/regex simples em `string` — ✅ Resolvido

Validar que um identificador só contém `[a-zA-Z0-9_-]` hoje exige `split("")` + iterar caractere por caractere comparando contra uma string de caracteres permitidos (`allowed.contains(c)`) — funciona, mas é código de baixo nível para uma tarefa comum (slugs, ids, validação de formulário). Um método `matches(pattern: string): bool` (regex simples) ou ao menos predicados de classe (`is_alnum()`, `is_ascii_letter()` por caractere) reduziria esse boilerplate em qualquer `tool` de validação.

> **Status:** `string.matches(pattern: string): bool` implementado — regex RE2 (sintaxe do pacote `regexp` do Go), comparando a string **inteira** contra o padrão (convenção Java/Kotlin, não "contém um match" como JS/C#), e um padrão inválido levanta erro catchable. Implementado em `internal/engine/interpreter/eval.go` (`callValueMethod`); catálogo do LSP atualizado em `internal/lsp/signatures.go`/`symbols.go`; exemplos em `sample/syntax/string_methods/matches.mh` e `matches_invalid_pattern_errors.mh`.

## 15. `input` de tipo `enum` não coerce o valor externo — schema anuncia `enum`, mas o binding não

Achado ao re-verificar o item 9 depois do `beta.6` (não fazia parte do relato original). O projetado `"enum": [...]` no `inputSchema` (item 9, já corrigido) é só metade do problema: quando um `workflow`/`pipeline` com `input action: ActionType` (`enum ActionType { Create, List, Get }`) é chamado **de fora** — `mhl run --input action=Create` ou `tools/call` via MCP com `{"action": "Create"}` — o valor chega e permanece uma `string` comum, não o valor tag distinto do `enum`:

```
type_of(action)              // "string", não "enum"
action == ActionType.Create  // false, mesmo com action valendo "Create"
match action { ActionType.Create -> ... }  // "no arm matched value Create"
```

Isso quer dizer: (a) hoje não há validação de fato do valor recebido contra as variantes do enum no momento do binding — `action=Bogus` não é rejeitado na entrada, só falha mais tarde e de forma confusa (`match: no arm matched value Bogus`) dentro do primeiro `match`/comparação que o tocar; (b) um `enum` em `input` de workflow servido é hoje inutilizável para o padrão idiomático (`match`/`==` contra a variante) — o step precisa comparar contra a **string literal** (`action == "Create"`), o que anula a vantagem de declarar `enum` para começo de conversa (`nameof`/checagem exaustiva do `match` não ajudam se o valor nunca chega como enum de verdade).

**Sugestão:** no binding de `input`/argumento de chamada externa (`mhl run --input`, `tools/call`), quando o tipo declarado é um `enum`, validar a string recebida contra as variantes declaradas (rejeitar cedo, com uma mensagem clara, se não bater com nenhuma) e coagir para o valor tag do enum antes de expor a variável ao corpo do `pipeline`/`workflow` — o mesmo espírito da coerção que já deve acontecer para `number`/`bool` vindos de string na CLI. **Ação nossa enquanto isso não for corrigido:** o Senpai não usa `enum` em `input` de workflow servido por MCP — `action`/`item_type` do `WorkItem` continuam `string` simples validada por `tool` (`.matches(...)`/`.contains(...)` em cima de uma lista permitida), documentado como decisão deliberada no plano macro (C7).

## 16. `router.select` não é um método consultável de fora — só `.delegate()` é público, e isso não é dito claramente

Achado ao adotar `codex` como segundo backend (item 11) atrás de um `router` para decidir Claude vs. Codex por chamada. A doc de `router` (Docs-Reference/Docs-Specification §"router") descreve `select` como "One-parameter lambda" — parece, à primeira leitura, um método comum do router, chamável como `Router.select(prompt: ...)` quando o chamador precisa saber ANTES de rodar qual agente será escolhido (nosso caso: Claude e Codex exigem formas diferentes do mesmo argumento `schema:`, então era preciso decidir o formato antes de montar a chamada). Na prática, `select` é só um hook de configuração que o runtime invoca internamente dentro do próprio `.delegate()` — chamar `Router.select(...)` de fora falha em runtime com `undefined variable "Router"`, **mesmo dentro do mesmo arquivo que declara o router, sem nenhum import envolvido** — confirmado por spike isolado (2 variações mínimas, uma com `tool` chamando `.select()`, outra com um `step` de pipeline chamando `.select()` diretamente; as duas falham do mesmo jeito). `.delegate(prompt:, schema:)` é o único método realmente exposto, e a doc já diz isso ("exposes one method") — a lacuna é que a assinatura de `select: (prompt) -> ...` sugerida na tabela de propriedades do router lê como convite a reutilizá-la como função pura de fora, quando na verdade é opaca.

**Sugestão:** (a) deixar explícito, logo na primeira menção de `select` na doc de `router`, que não é um método chamável — só um hook interno de `.delegate()`; um aviso ao lado do exemplo de código evitaria a leitura errada; ou (b) expor de fato um `Router.select(prompt: ...): string` público, já que é uma função pura sem side-effect (mesma assinatura declarada) — permitiria compor a decisão de roteamento com lógica que precisa saber o resultado antes de chamar `.delegate()` (nosso caso de uso: escolher a FORMA de um argumento auxiliar de acordo com o agente que será escolhido). **Ação nossa enquanto isso não existir:** abandonamos `router` para esse caso — `tool AgentSelector { pick(prompt): string -> nameof(Codex) }` + `match AgentSelector.pick(...) { nameof(Claude) -> Claude.run(...); nameof(Codex) -> Codex.run(...) }`, chamado direto em `workflows/shared/agents.mh` (`tool Writer`), resolve o mesmo problema com uma função comum, às custas de perder o `decider`/cascata de decisão por LLM que `router` ofereceria de graça.

## 17. `agent.after` só pode devolver `string`/nada, e só enxerga variáveis do `step` que chamou — não de um `tool` intermediário

Dois achados relacionados, os dois via spike, ao tentar fazer `after` devolver `{content, tokens_in, tokens_out}` (um objeto) em vez de só o conteúdo limpo:

1. **`after` rejeita objeto no retorno.** `after: () -> { return {content: ..., tokens_in: ..., tokens_out: ...} }` falha em runtime com `"<Agent>.after must return a string (or nothing), got object"` — só descoberto ao rodar de verdade (`mhl lint` não pega, porque não há checagem estática do tipo de retorno de `after` contra essa regra). A doc (Docs-Reference §"agent"/`after`) não deixa claro, na assinatura, que o tipo de retorno é restrito a `string`/`void` — lê como "hook livre para pós-processar `result`".
2. **`after` só enxerga o escopo do `step` de pipeline que fez a chamada — nunca de um `tool` intermediário.** O padrão idiomático pra extrair metadados extras (ex. contagem de token) é `after` fazer atribuição por efeito colateral numa variável que já existe no escopo de quem chamou (`tokens_in = ...`), aproveitando que "`after` vê as variáveis do step que chamou" (Docs-Reference §05) — funciona perfeitamente quando `Agent.run(...)` é chamado direto de dentro de um `step`. Mas se a chamada `Agent.run(...)` está dentro de um `tool` (ex. um adapter `Writer.generate(...)` compartilhado, chamado por vários `step`s de vários `workflow`s — exatamente o padrão que este projeto adotou pra não duplicar a config de agente em cada workflow), `after` não enxerga as variáveis do `tool`, e muito menos as do `step` que chamou o `tool` — a atribuição falha com `undefined variable "<nome>"`, mesmo a variável existindo no `step` original dois níveis acima. Confirmado por spike: um `tool Caller { go() -> Agent.run(...) }` chamado de um `step` com a variável declarada no escopo do `step` reproduz a falha de forma isolada e mínima.

Juntos, os dois achados inviabilizam o padrão "`tool` adapter compartilhado em cima de `agent.run(...)` que centraliza extração de uso/normalização de conteúdo" pelos dois caminhos óbvios (retornar um objeto rico de `after`, ou side-effect em variável do chamador) — sobra só devolver a `string` crua e processar tudo DEPOIS do `.run()` retornar, na própria linha de chamada.

**Sugestão:** (a) documentar explicitamente, na assinatura de `after` na doc de referência, que o retorno é restrito a `string`/nada — hoje só aparece como erro de runtime, não como contrato declarado; (b) considerar permitir que `after` devolva um valor estruturado (não só `string`) quando o chamador espera um tipo composto — hoje isso força todo metadado extra (custo, tokens, latência) a sair por um canal separado do valor de retorno de `.run()`, nunca junto; (c) considerar estender a visibilidade de `after` para escopos de `tool` intermediários (não só o `step` de pipeline mais externo), já que "quem chamou" nem sempre é um `step` diretamente — importante para qualquer app que queira um adapter de agente reutilizável entre múltiplos workflows sem duplicar a declaração do `agent` (nosso caso, C7 do plano macro). **Ação nossa enquanto isso não muda:** nenhum `agent` deste projeto declara `after` mais — `Claude`/`Codex` (`workflows/shared/agents.mh`) devolvem o stdout cru do CLI sem hook nenhum, e `tool Writer.generate(...)` extrai uso (`UsageParser`) e normaliza conteúdo (`StructuredOutput`) explicitamente depois de receber essa string de volta, na mesma função que fez a chamada — sem depender de visibilidade ambiente de variável nem de retorno estruturado de `after`.

**Achado relacionado, mesma classe, fora de `agent`/`after` (Fase 5):** `self.<metodo>(...)` — chamada de método-irmão dentro de um `tool` (item 6 desta lista) — tem exatamente a mesma limitação de escopo: o método chamado não herda variáveis locais do método chamador, só enxerga seus próprios parâmetros. `tool WikiActions.commit_ingest(project_id, data)` chamando `self.log("ingest", ...)`, onde `log(action, description)` não recebia `project_id` mas `WikiLog.append(...)` (chamado de dentro de `log`) precisava interpolar `${project_id}` — falhava com `undefined variable "project_id"` em runtime, todo `ingest`, não só via `after`. Reforça que o limite não é específico de `after` — é geral: nenhuma chamada indireta (`self.`, `after`, `router.delegate` com parâmetro extra — item 16) herda escopo de quem a originou; só parâmetros explícitos atravessam a fronteira. Detalhes em [FASE5-ACHADOS.md §5](FASE5-ACHADOS.md).

## 18. `env(...)` dentro de `agent.command`/`args` tem um contrato diferente de `env(...)` em qualquer outro lugar — falha fechado sem fallback possível, e o valor sai redigido

Ao resolver o item 11/16 pro backend Codex (dar a ele um `-C/--cd <DIR>` próprio, independente da CWD do `mhl` que o spawna — ver [FASE5-ACHADOS.md §2-3](FASE5-ACHADOS.md)), a primeira tentativa foi `args: ["--cd", env("SENPAI_CODEX_CWD"), ...]` direto no `agent`. Dois comportamentos not documentados, confirmados por spike isolado:

- **Falha fechado, sem fallback possível.** Em qualquer outro lugar da linguagem, `env(name)` devolve `""` pra uma var ausente (comportamento documentado: "An unset variable returns the empty string", Docs-Specification). Dentro de `agent.command`/`args` especificamente, uma var ausente faz `.run(...)` falhar com `"environment variable \"X\" is missing or empty"` — sem chance de fallback inline, porque `if/else` dentro do array literal de `args:` TAMBÉM falha (`undefined variable "env"`), sugerindo uma superfície de expressão mais restrita ali do que dentro de um `tool` comum.
- **Redaction automática.** O valor resolvido por um `env(...)` usado assim é registrado pro mecanismo de redaction do `mhl` — `mhl run --format json` devolveu `"--cd [REDACTED] hi"` num spike mínimo passando um diretório comum, não uma credencial.

Faz sentido para uma credencial de verdade (`env("API_TOKEN")` em `headers:`, o caso de uso original do item 1 desta lista) — mas não há como declarar "este `env()` aqui NÃO é sensível, use o comportamento padrão da linguagem" para um valor não-secreto (caminho de diretório, feature flag, etc.) que só por acaso também vem de uma env var.

**Sugestão:** documentar essa diferença de contrato explicitamente na doc de `agent`, já que hoje só aparece como dois erros de runtime inesperados; considerar um jeito de optar por fora do tratamento-de-credencial pra um `env(...)` específico usado em `command`/`args` (ex. uma segunda função, `env_plain(...)`, ou uma flag) — ou ao menos permitir um fallback declarativo (`env("X") ?? "default"`) sem perder a redaction pra quem quer isso de propósito. **Ação nossa enquanto isso não muda:** contornado computando o valor num `tool` comum (`env(...)` ali se comporta normal — `""` pra ausente, sem redaction) e referenciando a **chamada do tool** como elemento de `args:` — funciona porque `args:` aceita qualquer expressão (item 1), não só uma string interpolada; `tool CodexCwd` em `workflows/shared/agents.mh`.

## 19. `agent.run(...)`/`router.delegate(...)` só interpolam `${prompt}`/`${schema}` em `args:` — parâmetros extras nomeados na chamada não chegam lá

Confirmado por spike direto: `Agent.run(prompt: "hi", cwd: "/tmp/x")` com `args: ["--cd", "${cwd}", "${prompt}"]` devolve literalmente `"--cd ${cwd} hi"` — `${cwd}` nunca é substituído, mesmo sendo um parâmetro nomeado real passado na chamada. `prompt`/`schema` são os únicos dois placeholders "conhecidos" pelo mecanismo de interpolação de `args:`; qualquer outro nome de parâmetro passa despercebido, sem erro nenhum (nem em lint, nem em runtime) — só um `${...}` literal no argv final, silenciosamente errado.

Já valia para `router.delegate(...)` (achado que motivou o item 16 desta lista — abandonar `router` a favor de `tool AgentSelector` + `.run()` direto); esta fase confirma que o mesmo limite vale igual numa chamada direta `.run(...)`, sem router no meio nenhum — não é uma limitação de `router`, é de `agent.run(...)` propriamente.

**Sugestão:** (a) `mhl lint` poderia sinalizar um `${nome}` em `args:`/`command:` que não corresponde a `prompt`/`schema` nem a nenhum `${...}` reservado conhecido — hoje passa silenciosamente, e só se descobre em runtime inspecionando o argv real recebido pelo processo filho; (b) considerar estender a interpolação de `args:` para aceitar qualquer parâmetro nomeado da chamada (`.run(prompt:, schema:, cwd:)` → `${cwd}` disponível), não só os dois reservados — eliminaria a necessidade do contorno via `tool` do item 18 para qualquer valor que só precise variar por chamada (nem todo caso é uma env var/valor fixo de processo como `CodexCwd`). **Ação nossa enquanto isso não muda:** todo valor extra que um `agent` precisa em `args:` é resolvido como expressão avaliada na própria declaração (`tool` chamado diretamente no array de `args:`, item 1), nunca como parâmetro de chamada — funciona pra um valor fixo por processo (CWD, feature flag), não serviria pra um valor que precisasse variar por chamada individual (não é o nosso caso hoje).
